## Goals / Non-Goals

**Goals:** one time-current model behind the existing trigger seam; heat accumulation per phase; presets; safety %; cooling as an extra restore condition.
**Non-Goals:** changing give-way order, the ledger, room gate, pacing or fresh-sample guard; planner behaviour; per-phase planning (separate backlog item); the EV phase-switching logic; editing `docs/RELEASE_NOTES.md`; the slow-tick warning (exists).

## Decisions

1. **New pure module** `executor/fuse_model.py`: preset curves, log-log `trip_time_s(multiple)`, and `FuseHeatModel`, the default trigger. It holds per-phase heat and the build rate, and exposes `relief_needed(phase, momentary_a, now, stale) -> Relief` and `cooled(phases) -> bool` (all given phases below 50% heat), plus `heat(phase)` and `reset()`. No Home Assistant access.
2. **Reference is `main_fuse_a`**: multiple `m = current / main_fuse_a`. `target_margin_percent` is only the level a reduction brings the phase to, and the ramp-up and restore target.
3. **Heat rules**: let `start` be the first timed point of the curve (Typ C 1.13x, Diazed 1.25x, Custom the lower point). `m >= start`: `heat += dt / T(m)`, remember the build rate. `1.0 <= m < start`: hold. `m < 1.0`: `heat -= dt * last_build_rate`, floored at 0. `dt` is the time since the previous update of that phase; a gap above `max(120 s, 2 x interval)` is not integrated (heat holds), mirroring `CADENCE_MAX_GAP_S` and the engine's own gap guard (`executor/engine.py` ~3959).
4. **Curve anchors are assumptions**: Typ C 1.13x treated as 1 h and 5x as 0.1 s; Diazed 1.25x treated as 4 h, extended above 4x along the last segment slope. All values read from graphs, +/-30%.
5. **Trigger rule (the only detection point)**. `FuseHeatModel.relief_needed` is the implementation of the `relief_needed` seam; nothing else in `executor/load_balancer.py` compares readings with the fuse rating. Per phase and tick it first updates heat (fresh phases only), then reports relief when the action condition holds: `heat >= safety/100` or `T(m) * safety/100 < interval` (immediate cut). Result: `amount_a = max(0, momentary_a - main_fuse_a x target_margin_percent / 100)`, `urgent = immediate-cut condition`. Because `tick` already derives the pool from `amount_a`, the existing `binding < 0`/`binding_headroom < 0`, `hold_for_relief`, floor-degrade, 1-phase and shed paths pick it up unchanged; the reduction target is the target margin limit, so the phase falls below 1.0x and cools, otherwise the restore rule (heat below 50%) could never fire. Concretely the work in `load_balancer.py` is: widen the trigger contract (call per phase with `phase`, `now`, stale flag; hold the model on the `LoadBalancer`), delete the debounce and severe code listed in Context, and add the cooled gate (decision 7). `_degrade_at_floor` loses its debounce branch: at the floor with relief needed it goes straight to 1-phase relief or pause, since time is already in the trigger. The existing `urgent` handling (hold-for-relief bypass, `_urgent_phases`) is reused as is.
6. **Reading interval** is `executor.interval_seconds` (user decision; the balancer's measured `_tick_s` and sensor cadence exist but the spec keeps the configured interval so behaviour is predictable). The engine passes it to the model at construction and on config reload (engine.py 401, 536); it is not a `load_balancing` key.
7. **Restore gate**: the `ramp_up_window_s` comparisons for the EV (`_ev_reduced_at`, 999) and the battery (`_battery_reduced_at`, 1498) are replaced by `model.cooled(phases)`; the reduced-at markers stay as "a reduction happened" flags, cleared when a ramp is granted or as today. The gate is one more condition next to step pacing (`_pacing_ok`) and the room gate (`_grant_a`/`_room_a`); all must hold. `restore_shed` gets `model.cooled(entry.phases)` next to the existing `resume_delay_s`, `min_off_s` and room-for-power checks, so a water heater needs all three of room, `min_off_s` and cooling. Paused charger and battery re-fit (confirm window, target margin) are not heat-gated: they restart at their minimum within the margin. `ramp_up_window_s` stays only the averaging window; `increase_step_a`, `resume_delay_s` and `resume_confirm_s` stay.
8. **Shed timing**: with `pause_debounce_s`, `_ev_overload_since` and `_debounce_phases` gone, a shed load waits only through the existing pending-relief rule (an entry above reduced, paused or asked for 1-phase relief this tick, so its relief is unmeasured) and is ordered when the trigger still calls for relief afterwards or entries above are exhausted. No separate waiting state.
9. **Stale / missing**: the trigger gets the stale flag from `_is_stale`; for a stale phase it freezes heat and returns no relief. This changes nothing observable: stale EV and battery entries already take their fail-safe path before reading the pool, and shed is already blocked on stale phases by the fresh-sample rule. The old claim "immediate cut on a reading over the limit" is not what the code does and is dropped from the spec.
10. **Lifecycle**: heat is in memory only, 0 on restart; the model compares a signature (`fuse_preset`, custom points while Custom, `main_fuse_a`, safety) with the values it was built with whenever `LoadBalancer.config` is replaced and resets heat on change. Safety % alone does not reset heat (it is a threshold, not a curve).
11. **Config keys**: `load_balancing.fuse_preset` (`typ_c` | `diazed_gg` | `custom`, default `typ_c`), `fuse_safety_percent` (50-100, unset means 80 / 65 / 80 by preset), `fuse_custom_points` (two points, `overload_percent` 101-1000, `time_s` 0.5-86400, higher overload must have the strictly shorter time; prefill 130 % / 1200 s and 300 % / 4 s). Validation in `executor/config.py` (ranges next to 407) and `backend/api/routers/config.py`.
12. **Removed keys**: add `pause_debounce_s` and `severe_overload_percent` to `DEPRECATED_NESTED_KEYS["load_balancing"]` in `backend/config_migration.py` with a comment naming this change, after the `replan_after_throttled_s` entry. `remove_deprecated_keys` deletes them, logs, sets the changed flag; the startup path performs the atomic write with backup. `replan_after_throttled_s` stays removed and unsupported. Remove the keys from `config.default.yaml`, `executor/config.py` (fields 275-277, ranges 407-409, loader 612-633), `_validate_graceful_degradation_ranges` (and the imports 38, 43), `frontend/src/pages/settings/types.ts`, `search/guides.ts` and the tests. Keep `max_step_interval_s`, `write_deadband_percent`, `pending_timeout_s`, `phase_sign`, `min_on_s`/`min_off_s` and the custom `power_kw`/`power_sensor` as they are.
13. **UI**: preset select, safety % (placeholder shows the preset default), two custom points shown only for Custom, per `docs/design-system/AI_GUIDELINES.md`. The existing slow-tick warning stays; optionally extend its copy to say timing is coarser and cuts come earlier (text only).
14. **Specs**: delta specs MODIFY the affected requirements of `phase-load-balancing` and `load-balancing-settings` (full requirement text rebased onto current main, names unchanged) and ADD a requirement to `config-migration`.

## Risks / Trade-offs

- Curve accuracy is about +/-30%; Typ C uses the fastest band edge on purpose and the safety % covers the rest.
- With `executor.interval_seconds` at 60 (config.default.yaml) or 300 (code default) the heat integration is coarse and the immediate-cut region is wide; the existing 15 s advice and warning matter more now.
- A hot phase keeps calling for relief (heat >= safety) while the reading is between the target margin and the rating; that is intended (the fuse is hot) but means a load that steps up again right after a cut is reduced again.
- Hold-off weakness: the old `ramp_up_window_s` hold-off let the 60 s average flush pre-reduction samples. With a large overload heat cools from safety to 50% in seconds, and after an urgent cut on short ticks heat may already be below 50%, so the gate alone is weaker than 60 s. Pacing and the room gate remain, but a new house load can still look small in the average. See open question 1.
- Many tests pass `pause_debounce_s` or `severe_overload_percent` to `make_lb`/config and need editing; tests of the instant trigger need a fake trigger or a heat model with a tiny curve.
- The tick uses sampled currents; heat is an approximation of the real thermal state.

## Resolved Questions (maintainer, 2026-10-21)

1. Heat floor: while the trigger calls for relief, the phase heat is floored at `safety%` (requirement "Heat floor while relief is needed").
2. Paused charger / battery re-fit is not heat-gated.
3. Interval source is the configured `executor.interval_seconds`, passed in by the engine.
4. Diazed above 4x and Typ C 3x to 5x extensions with the 0.1 s anchor are kept; reading gaps longer than `max(120 s, 2 x interval)` are not integrated.
5. Custom point ranges (101-1000 %, 0.5-86400 s) are kept.
6. Tracker reset on custom-point change is kept.
