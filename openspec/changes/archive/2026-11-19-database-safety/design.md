# Design

## Context

Findings (read-only investigation, 2026-11-19; see proposal.md for motivation):

- Docker start-up (`scripts/docker-entrypoint.sh:78-108`) backs up `/data/planner_learning.db` with `cp` to `/data/backups/` on every start and migrates even if the copy fails. The compose file mounts `./data` at `/app/data` (`docker-compose.yml:21`) and the application and Alembic use the relative `data/planner_learning.db` (`alembic.ini:89`, `backend/main.py:157-160`). `/data` is only an empty directory created by the Dockerfile (line 95), so on a compose install the backup is skipped, and where it would run it lands in the container layer, which `compose up -d` discards on recreate. Not verified in a running container; derived from the files.
- Add-on `darkstar/run.sh:78-90` and the identical `darkstar-dev/run.sh` run `alembic upgrade head` with `DB_PATH=/share/darkstar/planner_learning.db`, no backup. `backend/main.py:79-88` runs no migration, it only logs.
- Alembic: 23 revision files. 22 have a non-empty `downgrade()` (several only re-create dropped tables empty or drop columns, losing data). 8 `tests/test_migration_*.py` files exist, only some of which call a downgrade, and nothing invokes a downgrade in production. The single-head assumption is not verified; `pre-migrate` handles several heads by comparing sets. Decision below: restore backups, never downgrade.
- Updater (`updater/service.py:232-365`): `_apply_steps` checks out, builds, `up -d`, polls the running version for 300 s. Build failure restores the checkout; `up -d` failure (343-348) and unhealthy start (360-365) restore nothing. The updater mounts `./data:/data:ro` (`docker-compose.yml:69`). `gate.py` only reads the alembic revision.
- Size: `data/planner_learning.db` is 819 MB (200,034 pages, `auto_vacuum=0`, WAL). By dbstat: `execution_log` 639 MB incl. indexes (78%; 364,862 rows, 18 Dec 2025 to 13 Nov 2026, about 1,100 rows/day, throttled to changes and heartbeats), `planner_debug` 41 MB (1,637 rows of about 25 KB, only written when `enable_planner_debug`), `slot_observations` 19 MB (35,076 rows), `price_forecasts` 33 MB (130,292 rows: 7 `days_ahead` per slot per issue), `slot_forecasts` 9 MB (49,146 rows), `slot_plans` 4 MB, `s_index_history` 5 MB (4,095 rows since 19 Jul, pruned inline), `learning_runs` under 1 MB (50 rows, all since 10 Nov because of the 30-day cleanup). Everything except `execution_log` and `planner_debug` is about 70 MB per 12 months, so keeping it forever is cheap (`price_forecasts` is the largest at about 57 MB per year). The 17 Oct to 11 Nov gap in the local copy is data, not a bug.
- Dead code: `ExecutionLog.cleanup_old_records` (`executor/history.py:279`) has no caller except `tests/executor/test_executor_history.py:404-437`; `history_retention_days` is parsed (`executor/config.py:1432`) and never read; `s_index_history` is pruned inline at 365 days on every planner write (`planner/observability/logging.py:13,68`); `learning_runs` is pruned by `LearningStore.cleanup_learning_runs(days_back=30)` at the end of every training (`ml/training_orchestrator.py:274`, a call outside `backend/` and `executor/` that an earlier grep missed). Both are therefore pruned already, by two more ad-hoc mechanisms.

Readers and the history each really needs:

| Table | Readers | Needs |
|---|---|---|
| `execution_log` | Executor page history list and CSV (`/api/executor/history`, paged, user date filter), `get_stats(days)` (UI default 7), `get_todays_slots` (today). Throttled, so monitors read the unthrottled `tick_stats` in `system_state`, not this table (`executor/tick_stats.py:1-8`). | audit trail; a month is enough |
| `slot_observations` | ML load/PV training reads all rows with 30-day recency half-life (`ml/train.py:181-259`, weight at 365 d is 0.0002), price training join (`ml/price_train.py:145`), reflex/learning windows 14 to 90 days (`backend/learning/reflex.py`, `store.py`), comparison history (full range), recorder backfill 10 days, price outlook 14 days | at least one full year for seasonality; user energy history |
| `slot_forecasts` | ML training LEFT JOIN, forecast accuracy and history views, learning metrics (joins observations) | same window as observations |
| `slot_plans` | plan-vs-actual deviation and benchmark joins with observations (`store.py:1133-1218`), schedule history overlay | same window as observations |
| `price_forecasts` | price model training (all rows joined to observations, half-life 30 d), planner price reserve (latest issue), UI accuracy (7 days) | about one year |
| `s_index_history` | written per planner run for calibration; no code or UI reads the rows back (the `s_index_history` field in `frontend/src/lib/api.ts:392` is the `schedule.json` debug section) | diagnostics only; one season is enough |
| `learning_runs` | UI learning history (`/api/learning/history`), learning stats, and the "graduation level" which is the run count (`backend/api/routers/forecast.py:76-90`: under 14 infant, under 60 statistician, else graduate; `store.py:1460-1475` uses 100) | the count must keep growing: with the 30-day cleanup a twice-weekly trainer can never reach 60 |
| `planner_debug` | nothing: written by `record_debug_payload`, `/api/debug` reads `schedule.json` | diagnostics only |

## Goals / Non-Goals

**Goals:**
- Every migration is preceded by a consistent backup and is undone automatically when it fails, in Docker, add-on and updater paths.
- The updater returns to the previous working version, code and database, when an update does not come up.
- The database stops growing, shrinks once, and stays compact without ever pausing the executor.

**Non-Goals:**
- Alembic downgrades, backups on a schedule, user-facing backup UI, off-site backups, signed updates and pinned origin (stay in the backlog), log rotation size caps, automatic adoption of new updater code by an already-deployed old updater (impossible, see D17), add-on automatic rollback (HA Supervisor owns add-on versions; the add-on gets the backup and the failed-migration restore).

## Decisions

**D1. Single Python module `backend/db_safety.py` with a CLI, no shell logic.** Commands: `pre-migrate`, `compact`, `restore`. Shell only calls it and propagates exit codes. Python is testable with pytest; the old shell `cp` is not. Alternative (bash `sqlite3` CLI): the images do not ship the `sqlite3` binary (also absent on dev hosts). Uses only stdlib `sqlite3`; imports `alembic` only to read the head.

**D2. Database path resolution** `DB_PATH` env, else `learning.sqlite_path` from `config.yaml` via `load_yaml`, else `data/planner_learning.db` (identical to `backend/main.py:157-160`), resolved against the current directory (`/app`). This fixes the `/data` vs `/app/data` mismatch. Backup folder is `<db dir>/backups` (`/app/data/backups` bind-mounted, `/share/darkstar/backups` for the add-on), which survives container recreation and is visible to the updater as `/data/backups`. The legacy `/host_backups` mount and old `planner_learning_*.db.bak` files are never touched; docs tell users they may delete them.

**D3. Backup trigger ("pending").** `pending = migration_pending or switch_pending`. `migration_pending`: DB file exists and is non-empty and its `alembic_version` set differs from `ScriptDirectory.get_heads()` (no table means legacy DB: pending). `switch_pending`: `PRAGMA auto_vacuum` is 0. Fresh/empty DB: nothing pending, no backup. A start with nothing pending touches nothing. Alternative (back up every start, as today): rejected, it is the 819 MB-per-restart bug.

**D4. Backup mechanism: `sqlite3.Connection.backup()` from a `mode=ro` connection**, same as the diagnostics snapshot (`backend/api/routers/system.py:399-425`), copying in 1024-page steps with 10 ms sleeps, then `PRAGMA journal_mode=DELETE` on the copy so it is one file, `PRAGMA quick_check` must return `ok`, then `os.replace` from `.tmp` to `pre-migration-<YYYYmmddTHHMMSSZ>-<from-rev or none>.db`. Alternative `VACUUM INTO`: rewrites the whole file (slower on 800 MB, needs temp space) and gives no benefit. Pre-check: free space on the backup volume must be at least DB size plus 64 MB, else the backup fails with a clear message. The `.tmp` is deleted on any failure.

**D5. Backup count: 3, constant `KEEP_BACKUPS = 3`, no config key.** Pruning sorts `pre-migration-*.db` by name (timestamp) and removes all but 3 after a successful backup only. After the first shrink the database is about 230 MB (it then grows about 80 MB per year because the learning tables are kept forever), so 3 copies cost about 700 MB; one is not enough because a restart loop of a failing release must not overwrite the only good copy (identical content, but a second failed attempt after a user restore could), and more than three is only disk. Prune happens only after the new backup verified.

**D6. Abort and restore semantics.** `pre-migrate` exits 1 if a backup was required for a pending migration and failed (migration never runs). If only `switch_pending` and the backup fails, it prints a warning, exits 0 and prints no path (the later `compact` receives an empty path and skips). On success it prints the backup path on stdout. If `alembic upgrade head` then fails, the script runs `restore <path>`: copy to `<db>.restore.tmp` in the db dir, `fsync`, `os.replace`, delete `-wal` and `-shm`; then exit 1. The container restart loop re-runs `pre-migrate`: the restored database is the pre-migration one, so each retry's backup has identical content (no data loss from pruning). Add-on scripts do the same; the existing `while read` pipe in `run.sh` hides alembic's exit code, so it is changed to run alembic with its output redirected to a temp file under `/share/darkstar` (not `/tmp`) and logged line by line afterwards, testing the real exit code.

**D7. Alembic stays the schema tool; no downgrade.** Backups restore data exactly, including data that a down-migration would drop. Not adding downgrade invocations also avoids trusting `downgrade()` functions that are mostly untested.

**D8. Retention defaults (per table, justified in the Context table). Decision of the user: the valuable learning data is kept forever by default.**

| Table | Key | Default | Min when positive | Reason |
|---|---|---|---|---|
| `execution_log` | `executor.history_retention_days` (existing) | 30 | 7 | Audit trail and Executor page list; no learner reads it; about 33k rows (about 60 MB) at steady state instead of 639 MB |
| `slot_observations`, `slot_plans`, `slot_forecasts` | `learning.retention_days` | 0 (forever) | 400 | Ground truth for ML and benchmarks, about 70 MB per year. A positive limit must exceed one full year (seasonality, models weight recent data with a 30-day half-life) plus margin, so 400 |
| `price_forecasts` | `learning.price_forecast_retention_days` | 0 (forever) | 400 | Price model trains on all rows; same seasonality argument as above |
| `s_index_history` | `learning.s_index_history_retention_days` | 365 (keeps the current inline behaviour) | 90 | Calibration/diagnostics only, no reader; one season is enough; 90 is the longest reflex window |
| `learning_runs` | `learning.learning_runs_retention_days` | 0 (forever) | 365 | Feeds the learning history UI and the graduation level (run count: 60 runs needs about 30 weeks at two trainings per week); under 1 MB per year |
| `planner_debug` | `learning.planner_debug_retention_days` | 14 | 1 | No reader, payload 25 KB each; two weeks covers a bug report |

`0` means keep forever and is accepted only by the three keys whose default is 0; `executor.history_retention_days`, `planner_debug` and `s_index_history` do not accept 0 (they would grow forever; 0 falls back to the default). Cutoff column: `execution_log.executed_at` (local ISO with offset, compared as text against a cutoff built the same way), `slot_*` and `price_forecasts.slot_start` (local ISO text), `planner_debug.created_at` and `s_index_history.created_at` (UTC ISO text), `learning_runs.started_at` (naive UTC `YYYY-MM-DD HH:MM:SS.ffffff` text). `price_forecasts` is pruned by target `slot_start`, not issue time, because training joins on `slot_start`. Local-time text comparison can be off by one hour across a DST change; irrelevant for windows of days. A positive user value below the minimum is raised to it (logged once), a non-number falls back to the default, so a typo cannot delete training data.

**D9. Cleanup implementation: one function `prune(db_path, retention, batch=5000, pause=0.2)` in `backend/db_safety.py`** using stdlib `sqlite3` with `timeout=30`: `DELETE FROM t WHERE rowid IN (SELECT rowid FROM t WHERE <col> < ? LIMIT 5000)`, commit, sleep, until 0 rows. It does not use the ORM or `ExecutionLog`, so one code path covers all eight tables and runs both at boot and at runtime. `ExecutionLog.cleanup_old_records`, its test class, the unused `ExecutorConfig.history_retention_days` field, `LearningStore.cleanup_learning_runs` with its call in `ml/training_orchestrator.py:274`, and the inline delete plus `S_INDEX_HISTORY_RETENTION_DAYS` in `planner/observability/logging.py` are deleted so retention has exactly one implementation. Visible consequence: `learning_runs` is no longer cut at 30 days, so the graduation level can now reach its thresholds (today it only counts runs of the last 30 days); the key itself stays and is read from `config.yaml` by the service. Alternative (call `cleanup_old_records` for one table and new code for the rest): two mechanisms, rejected.

**D10. Scheduling: `backend/services/db_maintenance_service.py`**, started in `backend/main.py` after the `LearningStore` init and stopped at shutdown (same shape as `installation_stats_service`, own asyncio task, not part of the planner scheduler so it keeps working when scheduling is disabled). Loop: first check 10 minutes after start, then hourly; run when `system_state` key `db_maintenance_last_run` is missing or 24 h old. The run executes `prune` then `incremental_vacuum` in `asyncio.to_thread`, writes the key (UTC ISO) only on full success, and logs a one-line summary with deleted rows per table. Any exception is logged and swallowed. Time of day does not matter because deletes are batched, so no fixed clock time (also works for installs that are not running at 04:00). Alternative (hook into `scheduler_service._loop`): it is gated on `enabled` and `current_task`, rejected.

**D11. One-time auto-vacuum switch is a start-up step, not an Alembic migration.** `VACUUM` cannot run inside a transaction and Alembic wraps each migration in one; a migration runs only when a revision is pending, but the switch is needed on databases that are already at head (the 819 MB case); and it needs disk-space logic that must be able to skip without failing, which a migration cannot do (a failed migration aborts start-up). So `compact` runs after `alembic upgrade head`, before uvicorn, in the same entrypoint and `run.sh`. Steps: if `PRAGMA auto_vacuum` is already 2 return "skipped"; if no verified backup path was given return "skipped" with a warning; `prune` (so the file to copy is small); compute used bytes (`(page_count - freelist_count) * page_size`) and require free space on the DB volume of at least `1.2 * used + 64 MB`, else warn and return "skipped" (the prune already done is legitimate retention and stays); set `SQLITE_TMPDIR` to the database directory so the vacuum temp file lands on the same volume that was checked, not RAM-backed `/tmp`; `PRAGMA auto_vacuum=INCREMENTAL; VACUUM;`; verify `PRAGMA auto_vacuum` is 2. Any exception is logged and the command exits 0 (VACUUM is rolled back by SQLite on failure; startup must continue). It is idempotent because the first check reads the stored mode. Running it before the executor and scheduler exist means nothing is blocked. Expected cost after prune: about 230 MB copy, seconds to a minute. Alternative `VACUUM INTO` + swap: more moving parts, no benefit.

**D12. Runtime vacuum: `PRAGMA incremental_vacuum(1000)` batches.** 1000 pages is 4 MB moved per call; each call is one short write transaction (tens of ms), executor and recorder writers wait at most that long within their 30 s busy timeout. Pause 100 ms between calls so writers always get the lock; stop when `freelist_count` is 0 or after a 120 s budget; then `PRAGMA wal_checkpoint(PASSIVE)` (never TRUNCATE/RESTART, they can block). Steady state frees only about the daily delete volume (about 1,100 execution rows), so a run takes well under a second; the 120 s budget only matters after a long outage or a lowered retention. Connection setting: if `auto_vacuum` is not 2 (switch skipped for low disk) the runtime does the prune but no vacuum and logs once. The service never executes a statement starting with `VACUUM`; a test traces all statements to prove it.

**D13. Rollback in the updater (Docker only), new `updater/db_restore.py` and `Updater._rollback`.** The updater image only contains `updater/`, so it cannot import `backend`; the restore is a small stdlib function (find newest `pre-migration-*.db` in `dirname(config.db_path)/backups` with mtime at or after the apply start minus 2 s; copy to temp, `quick_check`, `fsync`, `os.replace`, delete `-wal`/`-shm`). The backup itself is made by the new container's entrypoint right before it migrates, i.e. after the old container is stopped, so it is exactly the old database with no lost writes between a snapshot and the stop, and the updater needs no second backup mechanism. Flow in `_apply_steps` after checkout:
1. Record `prev_commit`, `prev_branch`, `prev_version = repo.current_version()`, `prev_channel = "dev" if prev_branch else "stable"` (matches how apply checks out: dev is on a branch, stable is detached), `started = time.time()`.
2. Build and `up -d` as today. Build failure: unchanged.
3. `up -d` non-zero, or no matching version in 300 s: `_rollback`.
4. `_rollback`: `compose stop darkstar` (also stops a restart loop); `db_restore.find_backup(since=started)` then `db_restore.restore` if a backup exists and the data directory is writable, else leave DB; `_restore(prev_commit, prev_branch)`; `compose build darkstar` and `up -d --no-deps darkstar` with `DARKSTAR_VERSION=prev_version`, `DARKSTAR_RELEASE_CHANNEL=prev_channel`, `DARKSTAR_COMMIT=prev_commit[:7]` (layer cache makes the build seconds); poll up to 300 s for `prev_version`.
5. State: `failed`, message "Update to X failed (<reason>). Rolled back to Y and restored the database backup." (or "...database unchanged"). If any rollback step fails: `failed` with the backup path and the manual command; no retry.
Compose change: updater `data` mount from `:ro` to read-write (`./data:/data`); the updater already controls the Docker socket, so this adds no privilege. Graceful degradation: `_rollback` checks `os.access(dirname(db_path), os.W_OK)` before restoring; on a still-read-only mount it does the code rollback and reports the manual restore command instead of failing. The updater gets the new mount through the self-recreate in D17. The existing test `test_unhealthy_after_up_fails_without_rollback` is rewritten. Not verified: whether `repo.current_version()` equals the string the running container reports for dev builds (`_version_from_file`), the existing health poll relies on the same equality for the target, and the rollback tests use the same fake.

**D17. Updater self-recreate after an apply (`updater/self_update.py`).** Facts: `_updater_outdated()` (`service.py:213-218`) compares the tree digest of the baked `updater/` copy with the repo at status time; a compose-only change (like the new mount) is invisible to it. The updater cannot run `compose up -d --build updater` itself, because compose would stop the container that runs the command. Design:
1. Fingerprint = sha256 of the `updater/` tree plus the bytes of `docker-compose.yml`; computed from the baked copy and the repo copy of the compose file at start-up, and from the repo at status time. `updater_outdated` is true when they differ.
2. After an apply that ends `done` (never after a rollback), if outdated and `state.self_update.fingerprint` is not already the current repo fingerprint, the updater writes `self_update = {state: "started", fingerprint, at}` to its state volume, removes any stale helper, and starts a detached helper from its own image: `docker run -d --name darkstar-updater-recreate --entrypoint sh -v /var/run/docker.sock:/var/run/docker.sock -v <repo>:<repo> <own image id> -c "sleep 3; exec docker compose --project-directory <repo> up -d --build --no-deps updater"` (own image from `docker inspect darkstar-updater`). The helper is a separate container, so it survives the stop of the updater; the 3 s sleep lets the status be persisted and polled.
3. Failure safety: `compose up --build` builds before it touches the running container, so a failed build leaves the old updater running. The old updater follows `docker logs -f` of the helper into its apply log (visible in the UI log and `log_tail`), then reads the helper exit code with `docker wait`: non-zero sets `self_update.state = "failed"` with the message "Updater could not be recreated, the old updater keeps working; run `docker compose up -d --build updater`", and removes the helper. If the updater is replaced, the new process on start-up compares fingerprints: equal sets `self_update.state = "done"`, different sets `failed`, and it removes the helper container.
4. No loop: at most one attempt per fingerprint (`self_update.fingerprint` is persisted whatever the outcome); a failed attempt is retried only when a newer repo fingerprint appears. Darkstar itself is never touched by a self-recreate failure. Residual risk, accepted: a new updater image that crashes on start restarts in a loop and the UI has no update feature until `docker compose up -d --build updater` is fixed by hand.
5. Status: `status()` adds `self_update` (`state`, `message`) and the UpdateCard shows it; the existing manual-command hint stays for the `failed` and old-updater cases.
First update (important limitation): the deployed updater runs the old code, which has neither rollback nor self-recreate, and nothing that Darkstar or the new compose file can do changes the code of a running updater (it only runs fixed git/compose commands; the Darkstar container has no socket). So the user-visible rule is: the update that first ships this change is applied by the old updater with the old read-only mount. Protected during that update: build failure (checkout restored, old container untouched, existing behaviour); a failed migration (the new container's entrypoint restores the pre-migration backup and exits, because that code is in the new image); a failed backup (migration aborted, DB untouched); the pre-migration backup is on disk for a manual restore. Not protected: an `up -d` failure or an unhealthy container after a successful migration (the old updater says "no automatic rollback was done"; the user restores with `python -m backend.db_safety restore` in the container or by copying the backup, documented in `docs/OPERATIONS.md`). After that update the already shown `updater_outdated` hint tells the user to run `docker compose up -d --build updater` once; from then on rollback and every later updater or compose change adopt automatically. A fully manual-free first hop is not achievable; this was reported to the user.

**D14. Add-on rollback = backup + automatic restore on failed migration only.** HA owns add-on versions and has no unhealthy-start hook for us; restore instructions go into `docs/OPERATIONS.md`.

**D15. New config keys** (approved by the user; defaults in `config.default.yaml`): `learning.retention_days: 0`, `learning.price_forecast_retention_days: 0`, `learning.s_index_history_retention_days: 365`, `learning.learning_runs_retention_days: 0`, `learning.planner_debug_retention_days: 14`; existing `executor.history_retention_days: 30` gets its comment corrected. No schema or Alembic change.

**D16. Tests (all automated, pytest, no manual steps).** Unit tests on temp SQLite files for backup, prune, switch, vacuum; script tests that run `scripts/docker-entrypoint.sh` pieces and both `run.sh` through stubs in the style of `tests/test_addon_run_sh.py` and `tests/test_docker_entrypoint.py`; updater tests with the existing fake docker and real temp git repos.

## Risks / Trade-offs

- [Retention deletes data a future feature wants] -> learning tables, price forecasts and learning runs are kept forever by default; positive values are floored at 400/400/365 days; documented.
- [Unbounded growth of the kept-forever tables] -> about 80 MB per year, accepted by the user; the opt-in limits exist for small disks.
- [One-time VACUUM on a large DB takes long or needs space] -> runs after prune, space-checked (1.2x used + 64 MB), temp dir on the same volume, skipped with a warning otherwise; rollback journal makes a crash safe.
- [First backup of an 819 MB database needs 819 MB free] -> checked up front; if it fails the migration is aborted with an explicit message (safe side); a switch-only start just skips.
- [Restore wipes rows written by the new version before it failed] -> acceptable: it never became healthy; documented.
- [Restart loop after failed migration] -> restored DB plus abort means no corruption; the updater stops the container before restoring; users without the updater get the loop and the log message naming the backup.
- [Updater must be rebuilt once to get rollback] -> unavoidable for the first hop (D17); existing hint plus docs; afterwards automatic.
- [Self-recreate helper fails or loops] -> one attempt per fingerprint, build-before-stop keeps the old updater, state and log visible in the UI.
- [Local-time text cutoffs across DST] -> at most one hour of error on windows of 7+ days.
- [Dead-field removal touches `ExecutorConfig`] -> tests grep-checked in task 5.1.

## Migration Plan

1. Release with the new code; existing installs upgrade through the normal path. First start: `pre-migrate` sees `auto_vacuum=0`, backs up (slow once, up to the DB size), `alembic` is a no-op if at head, `compact` prunes and vacuums once (819 MB becomes about 230 MB), uvicorn starts.
2. Docker users with the updater: the first update is applied by their old updater (see D17 for exactly what is protected); they run `docker compose up -d --build updater` once afterwards (the UI hint shows the command). Every later update self-recreates the updater when the updater or compose file changed.
3. Rollback of this change itself: the new code only deletes rows past the windows and changes the vacuum mode (readable by old code); restoring the first `pre-migration-*.db` brings back every row.
