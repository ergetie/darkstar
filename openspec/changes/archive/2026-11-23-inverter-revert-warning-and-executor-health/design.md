# Design

## Context

Verified in code:

- The executor runs every `interval_seconds` (default 300) and re-runs the whole profile mode each tick through `ActionDispatcher.execute`, which loops the mode's actions into `_execute_action`. For each action it resolves the entity (custom_entities, standard config, profile default), reads the state (`previous_value`), skips when `_values_match` says it already equals the target, otherwise writes and read-back verifies (`_verify_action`, up to 2 s). A reverted entity is therefore silently repaired on the next tick.
- The dispatcher already keeps per-entity write state: `_last_write_at: dict[entity_id, monotonic]`, set after every successful write. It has no record of the written value or of verification, so a per-entity baseline is a small addition next to it, keyed by the resolved `entity_id`. `_execute_action` has everything needed at the comparison point: `entity_id`, `entity_def.domain`, `previous_value`, the resolved target and `verification_success`.
- Entity domains are `select`, `number`, `switch`, `input_number`, `input_datetime` (`VALID_DOMAINS` in `executor/profiles.py`); `NUMBER_DOMAINS = ("number", "input_number")` is defined in `executor/actions.py`. `_values_match` already handles on/off vs True/False/"1"/"0" for switches and string compare for selects.
- Writes are suspended (no repair, no baseline) in these cases: `manual_override_entity` is "on" (`skip_writes`, engine tick), the executor is paused (tick returns, and `_run_loop` sleeps without ticking), the automation toggle is off (tick returns), the executor is disabled in config (`_run_loop` sleeps), or shadow mode is on (dispatcher skips writes). Quick actions and water boost are Darkstar's own commands.
- Existing alert pattern for engine-observed conditions: the engine persists a notice in `system_state` (`executor_ev_charge_notice`), `backend/monitors.py` evaluates it into an episode and `health_issues()` emits a snoozable banner; notifications go through `ActionDispatcher._send_notification`. Health issues carry a stable `code` which the snooze UI keys on.
- Power-mismatch is already covered by `backend/learning/battery_warnings.py` (`power_shortfall_warning`).
- Config save validation: `_validate_config_for_save` in `backend/api/routers/config.py` (introduced by 98d67d0d, REV LCL01) runs on `/api/config/save` and `/api/config/validate`. It returns `{"severity": "error"|"warning", "field"?, "message", "guidance"}`; errors block the save with 400, warnings are returned in the response and shown by the Settings form. It contains no `s_index` check at all, and neither do `backend/health.py` or `planner/pipeline.py _validate_config`; `planner/pipeline.py` and `planner/strategy/s_index.py` just `float()` the value (defaults `base_factor 1.1`, `max_factor 1.5` in `config.default.yaml`).
- Executor health check history: `get_executor_health()` was added to `backend/api/routers/executor.py` in c2e882ce together with `HealthChecker.check_executor`. 92e8960b (REV E2) converted it into the route `GET /api/executor/health` (`get_health`) and left `check_executor` importing the old name. The import raises `ImportError`, which the `except Exception` handler logs at debug level. No test imports it: `tests/backend/test_health.py` has no executor test.

## Watched discrete entities per profile

The watched set is every entity referenced by a profile mode action whose profile `domain` is not a number domain (so `select`, `switch`; `input_boolean` writes also take the switch path but no profile uses it). Verified in `profiles/*.yaml`:

| Profile | Watched entities (key: values written by the mode actions) |
|---|---|
| Fronius | `work_mode` (select, default none, user-mapped; all four modes distinct: Charge from Grid, Discharge to Grid, Auto, Block Discharging). `export_power_limit_enable` is a select in the entity registry but no mode action writes it, so it is not watched. |
| Deye | `work_mode` (select `select.inverter_work_mode`: "Zero Export To CT" for charge, self_consumption and idle; "Export First" for export), `grid_charging_enable` (switch `switch.inverter_battery_grid_charging`: on for charge, off for the other three) |
| Sungrow | `work_mode` (select `select.ems_mode`: "Forced mode" or "Self-consumption mode (default)"), `forced_charge_discharge_cmd` (select `select.battery_forced_charge_discharge`: Forced charge, Forced discharge, "Stop (default)"), `export_power_limit_switch` (switch `switch.export_power_limit`: written "on" in export mode only) |
| generic | `work_mode` (select, user-mapped, values `CONFIGURE_ME` until set), `grid_charging_enable` (switch, user-mapped). Skipped while the value is `CONFIGURE_ME` or the entity is unconfigured. |

Excluded as numeric: `soc_target`, `max_charge_current`, `max_discharge_current`, `grid_max_export_power`, `minimum_reserve`, `grid_charge_power`, `grid_discharge_power`, `export_power_limit`, `max_charge_power`, `max_discharge_power`, `forced_charge_discharge_power`.

Sungrow `export_power_limit_switch` is only written in export mode and never written off by another mode. A baseline for it would age across non-export ticks while the user or inverter legitimately changes it. Hence the rule in D2: a baseline survives only while the entity is part of the current mode's actions on consecutive ticks.

## Goals / Non-Goals

**Goals:**
- Warn when the inverter keeps leaving the value Darkstar commanded on a discrete entity, without false alarms from the executor's own writes, plan transitions, manual overrides, restarts or unavailable entities, and say which entity.
- Make the dead executor health check report the real executor state, with a test that catches a broken import.
- Warn at config save about an out-of-range `s_index.base_factor`.
- Universal: thresholds are constants derived from data/code, never one user's values.

**Non-Goals:**
- No change to executor write behaviour (still repair every tick). No automatic fix of any setting. No monitoring of numeric entities (deadband, rounding and clamping make exact comparison noisy). Power mismatch (done). No settings-sanity health warnings (PV confidence, capacity, efficiency, Settings UI hint): covered by the Learned Parameters section, `capacity_change_warning` and `pv_site_sanity.py`.

## Decisions

**D1 Per-entity baseline: the last verified value Darkstar wrote.** The dispatcher keeps `_verified_command: dict[entity_id, (value, monotonic_time)]` next to `_last_write_at`. An entry is set after a write whose read-back has `verification_success is True`. An unverified or failed write removes the entry. When the tick finds the entity already at the target and no write is needed, the entry is refreshed to that observed value without counting (the value is observed to equal the command). At the next tick, before the existing skip check, `previous_value` is compared to the entity's remembered value with `_values_match`. A plan transition changes the target but not the remembered value, so it never counts; only a state that differs from what Darkstar itself last set counts. Alternative (compare with the new target) rejected: fires on every normal transition.

**D2 What does not count (guards), applied per entity.** Only entities whose profile domain is not in `NUMBER_DOMAINS`. No event when: no remembered value (start-up, config reload that changes the resolved entity id, entry removed); `previous_value` is None/unavailable/unknown/empty; less than 30 s since the entity's last write; the last write was not verified; the entity value is `CONFIGURE_ME` or unconfigured; shadow mode. The dispatcher drops all baselines (a `clear_baselines()` method) when the tick does not write: manual override on, paused, automation toggle off, executor disabled, and when `update_config` swaps the profile or entity mapping. At the end of `execute()` it also drops baselines of entities that are not in the current mode's actions, so an entity that is written only in some modes (Sungrow `export_power_limit_switch`) is only compared across consecutive ticks that both write it. A user's manual change is therefore never reported and the first tick after resuming starts fresh. The dispatcher still repairs the value as today; the warning text tells the user to use manual override or pause when changing the inverter themselves.

**D3 Debounce: recurrence per entity in a window.** Events are kept per entity in the engine. An isolated event (firmware hiccup, one manual tweak) is logged at INFO only. A warning is raised when at least 3 events on the same entity fall inside a rolling window of `max(60 min, 4 x interval_seconds)`; events on different entities do not add up. With a 300 s tick the Fronius pattern (revert between most ticks) trips it in about 15 minutes. The warning lists every entity that currently has at least 3 events and clears when no entity does (no new event for one window). Constants live in one module-level block. Alternative (single event) rejected as noisy; alternative (2 consecutive ticks) rejected because the repair makes consecutive ticks unlikely.

**D4 Watch every discrete mode-action entity, not only `work_mode`.** The reported failure is `work_mode` on Fronius, but Deye `grid_charging_enable` and Sungrow `forced_charge_discharge_cmd` carry the charge vs idle vs export intent that `work_mode` cannot (Deye `work_mode` is identical for charge, self_consumption and idle). Numeric entities stay out: inverters round or clamp them, so exact comparison is noisy.

**D5 Surfacing follows the EV-notice pattern.** The engine persists `{active, since, updated_at, window_minutes, entities: [{entity, count, commanded, observed}]}` (`updated_at` is rewritten every writing tick while the condition holds; a notice not refreshed for 6 h is dropped as stale by the monitor) under a new `system_state` key `executor_mode_revert_notice` (no schema change; restart restores the notice, events restart from zero). `backend/monitors.py` gets an evaluator that turns an active, non-stale notice into a violation episode; `health_issues()` emits code `INVERTER_MODE_REVERT` (category `executor`, severity warning, snoozable, `details.entities` carrying the list). The code name is kept so the existing toggle and docs wording stay valid. The message names each entity with its commanded and observed values and event count; guidance: check the inverter's own schedule or app, the integration, firmware, and use manual override or pause for manual changes.

**D6 Notification.** `executor.notifications.on_inverter_mode_revert` (default true) gates one notification per episode via `_send_notification` (title "Darkstar Executor"), sent by the engine at the moment the notice goes active, not by the monitor, and naming the entity or entities. Wired exactly like `on_ev_soc_stale`: `NotificationConfig`, `load_executor_config`, `config.default.yaml`, executor router GET/PUT, Executor page toggle, Settings field, search guide.

**D7 Fix `HealthChecker.check_executor` against the real executor.** The original intent (c2e882ce): critical issue when the executor should be running but its thread is not alive; warning issue when the last run failed. The current equivalents are `ExecutorEngine._thread`, `config.enabled`, `is_paused` (a property), `status.last_run_status` and `status.last_error`; `GET /api/executor/health` computes the same. The fix:
- Add a read-only `peek_executor_instance()` in `backend/api/routers/executor.py` returning the existing singleton without creating one (`get_executor_instance()` creates and initialises an engine, which a health poll must not do). Move the status computation out of the route into a plain function `executor_health_snapshot(executor) -> dict` that both `get_health` and `check_executor` use, so there is one source of truth and no dead import.
- `check_executor` imports the snapshot function at module level in a way that fails loudly in tests, and keeps fail-open behaviour at runtime, but logs an import or attribute error at WARNING instead of DEBUG.
- Issues: critical `EXECUTOR_NOT_RUNNING` when `config.enabled`, not paused, and the thread is not alive; warning `EXECUTOR_LAST_RUN_FAILED` when `last_run_status == "error"`, with `status.last_error` in the message. Both carry a `code`.
- No instance (`peek` returns None) while the executor is enabled in config (read from the config file, since there is no engine to ask) is a critical `EXECUTOR_NOT_INITIALIZED` issue: startup initialisation failed or never ran. The check never creates an engine. When the executor is disabled in config, no instance is fine and gives no issue.
- Stale loop: warning `EXECUTOR_STALE` when the thread is alive, the executor is enabled and not paused, and `status.last_run_at` (set at the start of every tick in `_tick_unlocked`; the only last-run timestamp the engine has, verified) is older than `EXECUTOR_STALE_MIN_SECONDS`/`EXECUTOR_STALE_INTERVAL_FACTOR` derived threshold: `max(3 x interval_seconds, 600 s)`, named constants in `backend/api/routers/executor.py`. `last_run_at` None (no tick yet) gives no stale issue. The snapshot exposes `last_run_age_seconds`, `stale_after_seconds` and `is_stale`; `is_healthy` is unchanged by staleness. Known limitation: after a long disabled or paused period the old `last_run_at` can trigger one stale warning until the first tick after re-enabling (at most one interval).
- The existing `is_healthy` formula (`is_alive == should_be_running`) is wrong for a paused or disabled executor, whose loop thread stays alive while sleeping, so it reports an error for a healthy paused executor. The shared snapshot defines `should_be_running` as `enabled and not paused` and `is_healthy` as `not (should_be_running and not alive) and last_run_status != "error"`. This changes the `/api/executor/health` output only for the paused and disabled-but-alive cases (verify the Dashboard consumer in `frontend/src/lib/api.ts` and `Dashboard.tsx` before changing).
- Test: the check is exercised against a real `ExecutorEngine`-shaped object (a stub with the real attribute names, plus one constructed `ExecutorEngine` where cheap) and the import path is asserted by calling `check_executor` with a patched `peek_executor_instance`, so renaming or removing the function breaks the test. A second test asserts that an import failure does not raise from `check_executor` but is logged at warning level.
Note: enabling the executor through a config save did not start the thread (`reload_config` does not call `start`; only the enable endpoint and startup do). D9 fixes that; the critical issue still covers a thread that dies or never starts.

**D9 Config save starts the executor when enabled.** After `executor.reload_config()` in `/api/config/save`, when an instance exists and `executor.config.enabled` is true and its loop thread is not alive, the router calls `executor.start()` (idempotent, `executor/engine.py` `start`; the alive check avoids its "already running" warning on every save). No instance is never created here (the `EXECUTOR_NOT_INITIALIZED` issue covers it). Disabling: the loop re-reads config each iteration and idles (sleeps 10 s, no ticks, no writes) when `enabled` is false, so a save that flips enabled to false needs no `stop()`; the enable endpoint calls `stop()` only because the toggle is an explicit user stop. Config save therefore does not stop the thread (mirrors the loop's own idle path, and a later enable via save resumes without a restart). Failures are logged at warning and never fail the save.

**D8 `s_index.base_factor` save warning.** `_validate_config_for_save` has no `s_index` check (see Context), so a small block is added to it: when `s_index.base_factor` is a number and is below 1.0 or above `s_index.max_factor` (config value, default 1.5 when absent; the comparison with max is skipped when `max_factor` is not a number), append `{"severity": "warning", "field": "s_index.base_factor", "message", "guidance"}`. A non-numeric value is not handled here (existing planner `float()` behaviour is unchanged; no new error path). Warnings never block the save and are already returned by `/api/config/save` and `/api/config/validate`, so no UI work is needed beyond what already renders save warnings. The pure check is a small helper next to the other validators so it is unit testable.

## Risks / Trade-offs

- [Deye `work_mode` shares one value across charge, self_consumption and idle] -> `grid_charging_enable` is now watched too, so a charge vs idle revert on the grid-charging switch is caught.
- [Repeated repair writes are existing behaviour; warning does not stop them] -> Intended, detection only; guidance points to manual override.
- [HA state staleness right after a write could look like a revert] -> 30 s minimum age and a verified last write.
- [A user toggling an inverter switch by hand between two ticks looks like a revert] -> needs 3 events on the same entity in one window to warn; manual override suspends detection.
- [Entity only written in some modes would compare across a long gap] -> baseline dropped when the entity is absent from the current mode's actions (D2).
- [Health check no longer silently disabled: a not-running executor now raises a critical banner] -> intended; the check only fires when the executor is enabled and not paused.
- [base_factor warning could annoy users who deliberately use < 1.0] -> save warning only, never blocks.

## Migration Plan

No schema change and no config migration (new key has a default; absent key behaves as true). Rollback by reverting the change; the leftover `system_state` row is ignored.

## Open Questions

None. Resolved by the user: no instance while enabled is a critical `EXECUTOR_NOT_INITIALIZED` issue (D7); a stale loop raises `EXECUTOR_STALE` (D7); the "already at target" skip refreshes the revert baseline without counting (D1, unchanged).
