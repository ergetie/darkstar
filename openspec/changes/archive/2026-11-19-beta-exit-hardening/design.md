# Design

## Context

- `backend/main.py:313-319` installs `CORSMiddleware(allow_origins=["*"], allow_credentials=True)`. `create_app` returns `socketio.ASGIApp(ws_manager.sio, other_asgi_app=app)` (`main.py:444`), so Socket.IO traffic never sees FastAPI middleware; `backend/core/websockets.py:28-30` sets `cors_allowed_origins="*"`. Socket.IO has no client-to-server data handlers (`backend/events.py:51,61`). Tests and CI read `app.other_asgi_app` (`tests/api/*.py`, `scripts/ci_local.sh:52`, `.github/workflows/ci.yml:149`).
- Dockerfile verification: the image copies the whole backend package with `COPY backend/ ./backend/` (`Dockerfile:54`, `darkstar/Dockerfile:47`), so the new `backend/addon_bootstrap.py` is included; `run.sh` already puts `/app` on `sys.path`.
- Unit handling is duplicated: `normalize_active_power_kw` (`backend/core/water_heating.py:40-69`) handles W/MW; `ha_client.py:228,294-298` default to kW (kept); `ha_socket.py:801,877,944` and `executor/engine.py:5156` do inline `== "W"`; `system.py:131-134` skips conversion.
- The executor schedule loader (`executor/engine.py:2510-2580`) sets a warning only for no-`generated_at` and stale; the reset at `:2537` sits after early returns.
- The Dashboard "7-day price outlook" (`BatteryStrategyCard.tsx:515`, tooltip `:331-336`) prints SEK/kWh values as "öre". Source data is SEK/kWh (`backend/core/price_outlook.py:68,175-178`, `ml/price_forecast.py:49`); "Min/Max" are P10/P90 percentiles.
- `/api/config` returns the sanitized `config.yaml` including `nordpool.currency` and `timezone`; the frontend has no shared config context (`pages/Dashboard.tsx:127`).
- API timestamps are ISO with offset (`schedule.py:455-458`, `forecast.py:315,601`); calendar dates are plain `YYYY-MM-DD` in config timezone.
- `darkstar/run.sh` and `darkstar-dev/run.sh` are identical; the shell heredoc at `run.sh:36-46` rewrites `secrets.yaml` each start.

## Goals / Non-Goals

**Goals:** close the nine scope items with automated tests only; keep frontend API contracts unchanged; a single source each for currency, power-unit resolution and display timezone.

**Non-Goals:** optional API authentication, per-profile idle behaviour review, redaction of the full diagnostics bundle, multi-currency or Nordic features (Sweden-only stays), renaming `_sek` keys, backend timezone changes, a stable-channel add-on migration.

## Decisions

### 1. Cross-site write protection
1. Remove `CORSMiddleware`. Without ACAO headers browsers cannot read cross-origin responses; the frontend is same-origin (including HA ingress and the Vite proxy, which forwards browser headers unchanged).
2. New pure-ASGI `FetchSiteGuard` in `backend/middleware/fetch_site.py` wraps the outermost app so it covers HTTP, engine.io polling POSTs and WebSocket handshakes. It exposes `other_asgi_app` via a delegating property so existing tests and CI keep working.
3. Rule: for `http` scope with method POST/PUT/PATCH/DELETE reject with 403 `{"detail": "Cross-site request blocked"}` when `Sec-Fetch-Site` (value compared case-insensitively) is `cross-site` or `same-site`. Allow `same-origin`, `none` and absent (scripts, curl, HA, old clients). GET/HEAD/OPTIONS always pass. For `websocket` scope the same values deny the handshake (`websocket.close` code 1008, or `websocket.http.response.start` 403 when supported). `lifespan` passes through.
4. Same-site is rejected: it means another port or subdomain on the same host (for example another web app on the LAN server). Darkstar's own frontend is always same-origin, so rejecting same-site costs nothing and removes the "other local web app" attack path. Safe methods remain open so dashboards embedding GET data keep working.
5. Origin is NOT compared with Host (HA ingress proxy headers are not controllable or testable here).
6. Socket.IO `cors_allowed_origins=[]` (verified in `engineio/async_server.py:222`: `[]` skips CORS handling and emits no headers; `"*"` echoes Origin). `debug.py:243` reports the real value.
7. No extra-origins config key: no requester, and it would add schema surface. Alternative rejected: Origin allowlist (needs ingress knowledge).
8. Typed bodies: `PUT /api/executor/config` (`executor.py:383-390`) and `POST /api/executor/notifications` (`:496-503`) take a `dict`-compatible Pydantic model with `extra="allow"`; `/briefing` (`forecast.py:372-375`) uses the existing `BriefingRequest`. Handler logic is unchanged; invalid JSON yields 422.

### 2. Sensor unit overrides
1. New top-level `sensor_unit_overrides: {}` in `config.default.yaml`. Validation in `backend/api/routers/config.py`: keys match `^[a-z_]+\.[a-z0-9_]+$`, values exactly `W` or `kW`; otherwise a save error naming the entry. The config migration adds the key to existing files (existing default-merge behaviour).
2. Resolver in `backend/core/ha_client.py`: `resolve_power_unit(entity_id, reported_unit, overrides, *, path_key)` returns a `ResolvedUnit(unit, source)` where source is `reported` (non-empty HA unit, always wins, including a unit propagated from earlier history states), `override`, or `assumed` (unit `kW`). `normalize_power_for_entity(...)` wraps `normalize_active_power_kw` (W, kW, MW).
3. Unitless sensors are NOT made unusable. Without override they are read as kW exactly as today, so existing installs keep working after the update. A WARNING is logged once per entity per process: "No unit known for <entity>; assuming kW. Set its unit in Settings (sensor_unit_overrides)".
4. Routed through the resolver: `ha_client.py` (`:228`, `:294-298`, `:550/:580` unit propagation, `:946`), `water_progress.py:60-79`, `loads/service.py:224-245`, `executor/engine.py:5156`, `ha_socket.py:801/877/944` (now with MW), `system.py:131-134` (EV power converted). Overrides are loaded from `config.yaml` via a small cached accessor in `ha_client.py`; tests inject overrides directly.
5. Which sensors are power sensors is decided by the backend only. `backend/core/power_sensors.py` holds the single declarative registry of config path patterns that are read as power (for example `input_sensors.pv_power`, `ev_chargers[*].sensor`, `water_heaters[*].sensor`, `load_balancing.loads[*].power_sensor`) with a `path_key` each; `resolve_power_unit` takes that `path_key` from its caller. Two tests keep the registry from drifting: (a) every `path_key` passed to the resolver exists in the registry and every registry entry has a caller, and (b) a guard test fails if any backend or executor module reads `unit_of_measurement` for power outside the resolver. Adding a new power sensor type therefore means calling the resolver with a new `path_key` and adding one registry line; neither readiness nor the UI changes.
6. `unit_needed` computation: `compute_unit_needed(config, states)` expands the registry patterns against the given config, and for each referenced entity with a numeric live state, no HA unit and no override returns `{entity_id, settings_path, live_value}` (`settings_path` is the concrete path, e.g. `ev_chargers.0.sensor`). Readiness (`readiness.py:98-144`, `:262-300`) calls it, adds `unit_needed` to its response, and turns each entry into a `warn` check "<role>: no unit reported by Home Assistant. Choose W or kW for this sensor." with `action {kind: "set_sensor_unit", entity_id, path}`; with an override the check is `pass` with "(W, set manually)"; other unknown units keep today's warn. The existing per-role unit logic in readiness is replaced by this single computation.
7. New lightweight endpoint `POST /api/setup/sensor-units` takes a draft `{config: {...}}` body and returns `{unit_needed: [...]}` using live HA states and the same function, without running the planner or saving anything; it is the way the UI learns about not-yet-saved selections. The Fetch-Site guard allows it (same-origin).
8. UI, all backend-driven: the shared entity picker (`EntitySelect` as used by `EntityField.tsx` in onboarding and by `SettingsField.tsx`, `EntityArrayEditor.tsx`, `GiveWayListEditor.tsx`, `ExcessPvPriorityEditor.tsx` in Settings) gets a `useUnitNeeded` hook that posts the current draft config to `/api/setup/sensor-units` (debounced 300 ms, re-run whenever any picker selection changes) and a `SensorUnitSelect` rendered inside the picker whenever its selected entity id is in the returned list (match on `entity_id`). There is no list of fields in the frontend: onboarding and Settings pass their draft config to the same hook. The selector is a W/kW segmented control with design-system tokens (`docs/design-system/AI_GUIDELINES.md`) and writes `sensor_unit_overrides.<entity_id>` into the draft config, which triggers the refresh. The readiness warn row's "Set unit" button navigates to `settings_path` using the existing readiness action navigation.
9. Entities that report a unit keep the exact current rendering ("Current value: <state> <unit>", `EntityField.tsx:34-39`) with no selector.
10. Config save prunes `sensor_unit_overrides` entries whose entity is not referenced by any registry path, so stale entries cannot accumulate.

### 3. Schedule fallback alerting
1. `_stale_schedule_warning = None` is the first statement of `_load_current_slot`.
2. One helper `_no_valid_schedule(reason)` sets the warning for all five causes with texts ending "- no valid schedule, idle fallback" (not found with path, unreadable with `describe_exception`, empty, no `generated_at`, stale with age and limit).
3. Existing `notify_error` plus `_stale_schedule_alerted` dedupes per valid-to-invalid transition; a cause change while invalid does not re-notify; re-arm when a slot is found (`engine.py:1698-1700`). `tick_uncounted` already follows the warning.
4. The helper logs WARNING on the first occurrence of a transition and DEBUG afterwards, preventing per-tick flooding.

### 4. URL scrubbing
1. `scrub_urls` is applied in `describe_exception` before truncation. Any http(s)/ws(s) URL with a path beyond `/`, a query, fragment or userinfo is reduced to `scheme://host[:port]/<redacted>`; Discord webhook URLs become `https://discord.com/api/webhooks/<redacted>`; host-only URLs stay so the HA URL remains diagnosable. Patterns `token=`, `api_key=`, `key=`, `access_token=`, `password=` and `Authorization: Bearer ...` are masked outside URLs.
2. `notify.py` Discord path logs `type(e).__name__` and HTTP status only. The HA notify path keeps `describe_exception` (now scrubbed).

### 5. CI
1. `package.json` gets `"typecheck": "tsc --noEmit"`. `ci.yml` lint-frontend adds `pnpm typecheck` after ESLint and `pnpm build` after tests; `scripts/ci_local.sh` becomes `[x/8]` with typecheck, vitest and build, each guarded by `command -v pnpm`. `scripts/lint.sh` is left as is.
2. `tsc --noEmit` currently reports 0 errors (verified 2026-11-19), so no fixes are needed; the final group re-confirms 0 after the frontend edits.

### 6. Logs
1. `RotatingFileHandler(maxBytes=10 MiB, backupCount=5, encoding="utf-8")` replaces the timed handler (`logging.py:99-101`), default append mode so truncation by clear-logs is safe.
2. Clear-logs truncates the active file and deletes `darkstar.log.1..5`. Diagnostics adds `darkstar.log.1` when present (bounded bundle) and lists it in the manifest. Legacy `darkstar.log.YYYY-MM-DD` files are left alone; no one-time cleanup.
3. `docker-compose.yml`: `logging: driver json-file, max-size "10m", max-file "3"` for `darkstar` and `updater`.

### 7. Add-on bootstrap
1. Merge logic moves to `backend/addon_bootstrap.py` (`merge_ha_secrets`, `apply_addon_options`), called by `run.sh` as `python3 -m backend.addon_bootstrap`; this is unit-testable and the single writer. The shell heredoc `secrets.yaml` block is deleted.
2. With `SUPERVISOR_TOKEN`: set `home_assistant.token` always, `home_assistant.url = http://supervisor/core` when missing or empty; preserve every other key and comment (ruamel); never create `notifications`. Missing file: create with only `home_assistant`. Parse error: log, do not write. Standalone branch unchanged.
3. Remove dead options (`price_area`, `battery_soc_sensor`, `has_*`), `PRICE_AREA`, and their status-log lines; the status log prints config values without hardcoded fallbacks.
4. Timezone: schema `timezone: str?`, removed from default `options:` in `darkstar/config.yaml` and `darkstar-dev/config.yaml`. The option overwrites `config.yaml` timezone only when a non-empty string that differs; `export TZ` only when non-empty. `darkstar/run.sh` and `darkstar-dev/run.sh` stay byte-identical (test-asserted).

### 8. Currency
1. Single source: `nordpool.currency`, already served by `/api/config`; no new endpoint. `_sek` config keys, API fields and DB columns are NOT renamed: a rename is a config, database and API-contract migration over hundreds of sites and persisted user files with no user-visible gain. They are documented in a `currency.ts` comment as "amounts in the configured currency (legacy `_sek` suffix)"; `docs/` is untouched (ask-first).
2. `frontend/src/lib/currency.ts`: module store (`setCurrency`, `getCurrency`, `subscribe`), `CurrencyProvider` mounted once (fetches `Api.config()`, updated again after settings save), `useCurrency()`, and pure helpers `currencyInfo(code)` (table SEK to öre/100, NOK and DKK to øre/100, EUR to cent/100, others no subunit), `formatMoney(value, {currency, digits})`, `formatPrice(value, {currency, digits, unit: 'main' | 'sub'})` (the currency code is passed in the options object, not read from the store), `priceUnitLabel(currency, unit)`, `moneyUnitLabel(currency)`, plus `useCurrencyFormat()` which binds them to the store and `substituteCurrencyTokens`. Before load or with an empty or invalid code (which `setCurrency` resets to unknown on the frontend), helpers return the number without a unit. The ISO code is used everywhere; "kr" is dropped as ambiguous.
3. Static settings strings (`settings/types.ts`, `guides.ts`, `SettingsField.tsx`) keep `{currency}` and `{priceUnit}` tokens substituted in one place at render. `ChartCard.logic.ts` pure functions take the unit label as a parameter (tests updated). `BatteryStrategyCard`'s `ore()` becomes `formatPrice(x, {currency, unit: 'sub', digits: 0})` (or the bound `price(x, {unit: 'sub', digits: 0})`).
4. Tooltip: "Tue: 2.90 SEK/kWh", "P10: ...", "P90: ...", "Lowest hour: ...", "Highest hour: ...", from `min_hour_p50` and `max_hour_p50` (already in `PriceOutlookDay`).
5. Backend `backend/core/currency.py`: `get_currency_code(config)` (uppercase, 3 letters, fallback constant equal to the default-config value when the key is missing, empty or not a three-letter code) and `price_unit(config)`. Used in `strategy/engine.py` (5 messages), `analyst.py:191`, `config.py:1012/2009`. Log lines in `planner/solver/kepler.py:1371` and `planner/pipeline.py:1175,1176,1336` drop the unit text ("cost %.2f") because no config is in scope there.
6. Settings: onboarding currency field stays on `nordpool.currency`; if absent from `settings/types.ts`, add a select with SEK, EUR, NOK, DKK in the System tab. No VAT, tax or price-area changes.
7. A vitest guard test greps non-test frontend sources for `\bSEK\b|öre|\bkr\b` outside `currency.ts` (documented allowlist only).

### 9. Timezone
1. Two concepts. Display timezone is the browser's: `frontend/src/lib/timezone.ts` exports `displayTimeZone()` (`Intl.DateTimeFormat().resolvedOptions().timeZone`, fallback `UTC`) and `displayLocale()` (`navigator.language`). All clocks, tooltips and axis labels (`time.ts` `formatHour`, `ChartCard.logic.ts` `formatClock`/`formatTimeRange`, `ModelTrainingCard`, `Aurora`, `Executor`, `CommandDomains.buildPartialNotes`) use it with `hourCycle: 'h23'`. `sv-SE` is removed; date keys are built from `formatToParts` with `en-US`.
2. Plan timezone (`config.timezone`, `time_axis.timezone`) is kept only for backend-defined semantics: transfer-fee rule matching (`ChartCard.tsx:65,77,98`; fallback becomes `displayTimeZone()`), cost-series and comparison buckets (`CostSeriesChart`, `CommandDomains`, `costExclusion.ts`), and API calendar-date strings. Instants render correctly in any zone; buckets and tariff windows must not shift with the viewing device.
3. Dashboard day grouping (`isToday`, `isTomorrow`, `useChartSlots`, `ChartCard.tsx:1469-1470`) uses the browser day. History arrives as instants, so a test with browser `Pacific/Auckland` and config `Europe/Stockholm` proves no slot is dropped or duplicated across the 48 h seam.
4. Slot boundaries: all real zone offsets are multiples of 15 minutes, so 15/30/60 minute slot starts stay on quarter hours; hourly buckets in half-hour zones (Asia/Kolkata) are labelled `:30`, which is accepted. DST: every conversion uses `Intl`, never offset arithmetic; tests cover spring-forward and fall-back in the browser zone.
5. UTC-date bugs fixed with local-date helpers: `Dashboard.tsx:381-384`, `CommandDomains.tsx:75-119`, `Aurora.tsx:678-679`. `DesignSystem.tsx:47,228` sample timezones use `displayTimeZone()`; the `api.ts:85` comment is updated.
6. Tests mock `displayTimeZone` rather than relying on the process `TZ` pinned in `vitest.config.ts`. A guard test fails on `Europe/Stockholm` or `sv-SE` in non-test frontend sources outside a documented allowlist.
7. Backend timezone code and its `Europe/Stockholm` fallbacks are unchanged (Sweden-only).

## Risks / Trade-offs

- Add-on timezone: Supervisor keeps the stored options value for existing installs, so they still overwrite `config.yaml` timezone until the user clears the option. New installs are unaffected.
- Same-site rejection: a self-hosted setup serving the API from a different subdomain than the frontend would see 403 on writes; this is not a supported topology. Safe methods are unaffected.
- Unitless sensors keep being read as kW (no behaviour change for existing installs); users with W sensors lacking a unit keep the 1000x error until they act on the readiness item, which is surfaced in readiness and the entity picker.
- The backend power-sensor registry is the one place that lists power config paths; tests prevent drift, and the UI has no list.
- Day grouping uses the browser day while backend history uses the config day; viewers outside the configured zone may see the "today" boundary differ from planner days. Accepted and covered by the seam test.
- Sweden-only: only the currency table gets non-SEK entries; VAT, tax defaults and price areas stay Swedish.
- The idle-fallback behaviour per inverter profile and optional API authentication are not addressed (their backlog entries were removed at the user's request).

## Apply findings

- `POST /api/setup/sensor-units` cost (measured with a mocked httpx client, 20 calls): one `GET /api/states/<entity_id>` per distinct referenced power entity, run concurrently with `asyncio.gather`; a typical config references 3-10 entities. It does not call `/api/states` (the full list), the registry websocket or the planner, and caches nothing, so every call re-reads the entities. Latency is about the slowest single read plus ~4 ms of overhead (3 entities: 3.9 ms at 0 ms per request, 24 ms at 20 ms per request; sequential reads would add up). Entities that fail to read log one WARNING per call in `get_ha_entity_state` and are simply not listed. With the 300 ms UI debounce this is a few single-entity reads per selection change; readiness keeps using its existing discovery states and adds no request.
- Entity ids are matched against `^[a-z_]+\.[a-z0-9_]+$` before any URL is built, so a draft config cannot steer the request path.
- `path_key` is passed by callers that know the config path (input roles, EV, water heater, shed-load power sensor, EV phase sensors) and is optional for history parsing, which only knows the entity id. The drift tests check `path_key` constants and registry coverage by AST scan, and an allowlist of modules that legitimately read `unit_of_measurement` for non-conversion purposes.
- EV phase sensors (`ev_chargers[*].phase_sensor_l1..3`) are in the registry with `report_unitless=False`: a unitless phase sensor is read as amps, so it never appears in `unit_needed`; an override or reported W/kW still converts. The shed-load power sensor keeps its device-class rule (unitless with `device_class: power` is W) unless an override exists.
- The `ha_client` and `loads/service` literal `"kW"` passed to `normalize_active_power_kw` applies only the idle cutoff to values that are already kW, so it is not a unit read and was left unchanged.
- Frontend picker audit (verified by reading code, apply of 2.18-2.24). Every Home Assistant entity picker in Settings and onboarding is the shared `components/EntitySelect.tsx`; no bespoke entity selects exist. Users of it: onboarding `components/onboarding/EntityField.tsx` (the only onboarding picker; every step field goes through `EntityInput` in `steps.tsx`), Settings `SettingsField.tsx` (`entity` fields, including the generated inverter profile entities), `EntityArrayEditor.tsx` (10 call sites: water heater sensor/control, EV charger power sensor, plug, SoC, charging control, ready-by and other entities), `GiveWayListEditor.tsx` (2: custom-entity and shed-load power sensor) and `ExcessPvPriorityEditor.tsx` (1). The `<select>` elements in `EntityArrayEditor`, `GiveWayListEditor` and `NumberPresetInput` choose types or modes, not entities, and `ServiceSelect` picks notification services. Not covered: `ev_chargers[*].phase_sensor_l1..3` have a type declaration in `EntityArrayEditor.tsx` but no editor anywhere in the UI (config file only), so they cannot show a selector; their unit follows the registry rule (unitless is amps). Nothing else needed wiring.
- Frontend wiring: `lib/sensorUnits.ts` holds the `SensorUnitContext`, pure override helpers and `applyConfigPatch`; `lib/useUnitNeeded.ts` is the debounced hook. The picker reads the context, so onboarding (`OnboardingWizard.tsx`, draft = wizard config) and the Settings tabs that contain pickers (`useSettingsForm.ts` returns `sensorUnits`; draft = saved config with the form's save patch applied) use identical behaviour. Overrides are written as the whole `sensor_unit_overrides` map because entity ids contain a dot and cannot be dotted paths. Onboarding includes the map in a step's save patch only when it differs from the loaded one; Settings adds it to the patch and marks the form dirty.
- Selector stays visible after a choice: once an override exists the backend stops listing the entity, so a picker that showed the selector only while the entity is listed would hide it the moment the user clicks W or kW. The hook therefore also shows it for an entity the backend listed earlier in the session that now has an override. After a save and reload the override is persisted and the selector is shown only if the backend lists the entity, as the spec says; a saved choice is changed by clearing the entity or via readiness, which no longer lists it.
- The readiness "Set unit" button exists in the onboarding review step only, because that is the only UI that renders readiness checks; it reuses `fixStep(path)`/`onFix`, the same navigation as "Fix". Paths outside the onboarding steps (for example shed-load power sensors under `load_balancing`) fall back to the `system` step as "Fix" does, but they are only editable in Settings.
- `pnpm typecheck` does not exist yet (task 5.1 adds it); `npx tsc --noEmit` was used for task 2.18 verification.
- Correction (post-archive): `compute_unit_needed` lists every numeric power sensor with no HA unit and adds `override` (`"W"`, `"kW"` or `null`) to each entry; it is no longer filtered by override. Readiness warns only for entries with `override: null` and passes (manual unit) otherwise. The picker shows the selector for exactly the listed entities, preselected with the override, so the choice survives a reload; the client-side "listed earlier in the session" memory in `useUnitNeeded` was removed. Sensors with an HA unit are unlisted and unchanged.
