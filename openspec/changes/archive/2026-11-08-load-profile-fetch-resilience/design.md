# Design

## Context

See proposal.md for motivation. Verified current behaviour:

- `get_load_profile_from_ha` (`backend/core/ha_client.py` ~889-1000) loops over `_LOAD_PROFILE_DAYS = 7` windows of 24 h, awaiting `get_power_history_batch([entity], day_start, day_end)` one at a time. Any `None` returns `get_dummy_load_profile(..., discard_reason="'<sensor>' history could not be fetched from Home Assistant")`. Since the follow-up to `fix-unavailable-water-provenance` (per-slot coverage averaging, spec `energy-recording` "Load Profile Averages Over Measured Time"), each of the 96 local slots is averaged over the time it was validly measured, not divided by 7; gap-free history gives the same values as before.
- `get_power_history_batch` (~345-400) makes one `GET` with the existing positional `timeout: float = 12.0` on the shared plain `httpx.AsyncClient` (`get_ha_http_client`), no retry. `except Exception` logs `"%s", exc`; `httpx.ReadTimeout`/`ConnectTimeout` have an empty string, which gives the observed `get_power_history_batch(1 entities): `. A connection failure has text (prod 2026-11-06 06:45: `All connection attempts failed`).
- `get_dummy_load_profile` returns the synthetic curve when `input_sensors.synthetic_daily_load_kwh` is a positive estimate, otherwise `[0.5] * 96` and sets status `degraded/demo` with the discard reason as detail. So the "0.5 flat demo profile" is only the fallback without a synthetic estimate (the brief's wording is incomplete on this point).
- The degraded status is cleared only by `ml/forward.py` (`clear_load_forecast_status()` after a successful ML forecast). Nothing on the HA path clears it. `backend/health.py` `check_load_forecast` renders `demo`, `baseline` and `no_ml` reasons only.
- Consumers: `backend/core/forecasts.py` (~323 baseline fallback and ~746 daily totals, so two calls per planner run; ~452 re-fetches only in a fallback path), `backend/api/routers/ha.py` (~165, only when a history average is 0) and `backend/api/routers/debug.py` (~184). HA http clients are per event loop, so callers can run on different loops.
- Executor: `executor/actions.py` `_retry_with_backoff` logs `"HA API call failed (attempt %d/%d): %s. Retrying in %.1fs..."` with `e`. The HA client uses `aiohttp.ClientTimeout(total=5)`, so a timeout is `asyncio.TimeoutError`, whose string is empty. Prod 2026-11-05 has 320 such lines `HA API call failed (attempt 1/4): . Retrying in 1.0s...`. The final `HACallError` carries only the exception type name.
- `backend/core/open_meteo_retry.py` already has a bounded `retry_async` (fixed 3 attempts, 2 s / 4 s) with the same blank-message log (`%s` of `exc`). Its type set is aiohttp/requests, not httpx.
- `backend/core/atomic_json.py` `write_json_atomic` is the existing durable JSON writer; `data/` holds runtime state and runtime files are not committed.
- Prod runs an older build (`dev-261026.0611`, line numbers differ from HEAD), so the log evidence confirms the behaviour but not the exact HEAD line numbers.

## Goals / Non-Goals

**Goals:**
- A transient HA stall never replaces a real load profile with the demo profile.
- Bounded latency: the profile build never blocks a planner run beyond a fixed deadline, and an outage costs at most one deadline per cooldown window.
- Honest status and logs.
- Universal: thresholds are named constants with a rationale, no per-installation values.

**Non-Goals:**
- No retry change for the recorder, water progress or backfill callers (recorder timing is slot-critical).
- No change to the executor's 5 s write timeout (it exists to stop the executor freezing); only its logging changes.
- The profile slot mapping uses a hard-coded `Europe/Stockholm` (`local_tz` in `get_load_profile_from_ha`) while `forecasts.py` indexes by the configured timezone. Found while reading; a separate bug, not changed here.
- The 2026-11-05 17:40 "4510 kWh/day exceeds 500" discards are the already fixed unit-loss issue on the older prod build, not part of this change.

## Decisions

1. **Opt-in retry and timeout for history chunks.** `get_power_history_batch` already takes `timeout: float = 12.0`; only an `attempts` argument is new (default 1) and the `timeout` type widens to `float | httpx.Timeout` so the profile build can pass connect and read limits. A keyword-only `deadline` (monotonic clock value) is also opt-in: it caps each attempt's timeout to the time left, shortens the backoff sleep and ends the retries once passed, which is how the 60 s deadline of decision 2 is enforced inside a chunk. The shared `retry_async` takes an optional `source` name for its log line (default Open-Meteo) so the history retries are not logged as Open-Meteo. Defaults keep one attempt and 12 s so existing callers are unchanged. The profile build passes 3 attempts, backoff 1 s then 3 s, and a per-attempt timeout split into connect 5 s and read 20 s (about six times a normal ~3.2 s day request, long enough for a loaded HA, short enough to retry inside the deadline). The retry classifier is httpx-aware: `httpx.TimeoutException`, `httpx.ConnectError`/`NetworkError`, `RemoteProtocolError`, HTTP 5xx and 429 are transient; other 4xx are not. The existing `retry_async` in `open_meteo_retry.py` is generalised (optional attempts/backoff parameters, defaults unchanged) rather than duplicated.
   - Alternative: raise the single timeout to 30-60 s. Rejected: one stalled attempt still costs the full wait and gives no second chance after HA recovers.
   - Alternative: retry inside every caller. Rejected: recorder timing.
2. **Deadline and early abort.** The whole profile build has a 60 s deadline; each attempt's timeout is capped by the time left. Two consecutive chunks that exhaust their retries abort the loop (HA is clearly down) so a hard outage costs about the deadline once per call, not 7 times. Chunks stay sequential to avoid loading a struggling HA.
3. **Partial windows are used, with a floor.** This builds on per-slot coverage averaging (`integrate_power_points_covered` plus `_coverage_averaged_profile` in `ha_client.py`), which is already in place and is a dependency of this change. Each slot is its summed energy over its covered seconds, scaled to 900 s, so a day that was never fetched simply contributes neither energy nor covered time. No separate "divide by days fetched" step is added: a failed chunk is a chunk with zero coverage, and the slots, the exact partial-slot handling, the interpolation of slots with under one slot length of data and the 48-of-96 minimum supported slots all apply unchanged. The profile is a mean of 24 h windows each covering all 96 time-of-day slots, so losing a window loses precision, not time-of-day coverage and not systematically one hour of the day. Failures cluster in time (HA stalls), not by weekday or hour, so no directional bias is introduced. The floor is a majority of the window (`ceil(7 / 2) = 4` days fetched) because below that the sample is too thin to beat a complete stored profile; it is counted in days fetched, separately from slot coverage. **Order of the two rules:** (1) fetch completeness first: fewer than 4 days fetched is a transient failure (stored profile, then synthetic/demo, and it starts the cooldown), whatever the fetched data looks like; (2) only then the data-quality rules on what was fetched, unchanged from a complete window: no valid point (empty history), fewer than 48 of 96 supported slots, and the 500 kWh/day and non-positive bounds each return the demo or synthetic profile with their existing message, do not use the stored profile and do not start the cooldown. So a window of 4 or more days that still has under 48 supported slots is a data problem, not an outage, because the fetched data is all the history there is for the sensor; a window of under 4 days is never judged on its data. A partial result sets status `partial`, informational, naming `N of 7 days`. It is stored as last good only when it meets the floor, with `days_used` recorded.
   - Alternative: divide by the number of days fetched. Rejected: it would be wrong whenever a fetched day also has sensor gaps, and it would duplicate the coverage logic.
   - Alternative: all-or-nothing as today. Rejected: it turns one slow request into a flat 0.5 kWh profile (verified in prod).
   - Alternative: any number of days. Rejected: one day of data is a weak, weekday-biased estimate.
4. **Fallback order.** (1) full live profile, (2) partial live profile with at least the floor, (3) last good profile within the maximum age, (4) existing synthetic or demo fallback. Steps 2 and 3 apply only to transient fetch failures. Empty history, implausible data, an unconfigured sensor and the 500 kWh/day bound keep their current behaviour and messages (spec `load-history-sanitization`), so real data problems are not hidden behind an old profile.
5. **Last good profile: content, age, persistence.** Stored as `data/load_profile_last_good.json` via `write_json_atomic`: `{version, sensor, built_at (UTC ISO), days_used, days_total, profile[96]}`; also kept in a module-level variable so a failed disk write or read does not matter. Maximum age 7 days: that is the window the profile summarises, and beyond it the stored data shares no day with a fresh window; the age is always shown in the status. A stored profile is rejected when the sensor differs, the timestamp is in the future or unparsable, `version` is unknown, or it is not 96 finite non-negative numbers whose total is within `0 < total <= 500`. Write only after a successful full or floor-meeting partial build; a failed write is logged with the exception type and ignored. Add the file to `.gitignore` (runtime data, per AGENTS.md).
   - Alternative: memory only. Rejected: a restart during an outage (the situation that matters) would lose it.
   - Alternative: SQLite learning DB. Rejected: schema change (ask first) for 96 numbers.
6. **Truthful status.** New degraded reasons in `backend/health.py`: `stale` ("Load forecast using stored profile from <age> ago", detail names the sensor and that history could not be fetched, warning) and `partial` (info, "built from N of 7 days"). `check_load_forecast` renders both; the `demo` text stays only for the demo profile. A full live build calls a narrow clear that only clears `stale`, `partial` and `demo` set by the HA path (not `baseline` or `no_ml` from the ML forecast). Because the `demo` reason today persists until the ML forward pass clears it, this also fixes a lingering banner after HA recovers. Log level for fallback stays WARNING; the log line states which fallback was used.
7. **Never-blank errors.** One small helper `describe_exception(exc)` returns `TypeName: text`, or `TypeName` plus `repr` when the text is empty, with a length cap. Used in: `get_power_history_batch`, the broad `except` in `get_load_profile_from_ha`, the retry log of the shared retry helper, and in `executor/actions.py` for the retry log and in the message of the final `HACallError` (`HA API call failed after N attempts: <description>`); `HACallError.exception_type` stays the bare type name because callers and tests compare it. The helper is `backend/core/exception_text.py`. The helper lives in `backend/core` and is imported by the executor lazily like its existing `backend.*` imports (the executor module already imports `backend` lazily). If that import direction is rejected in review, the helper is duplicated in `executor/` (4 lines).
   - Other `except Exception as e: logger...("%s", e)` sites in `executor/actions.py` (for example `Failed to write to %s: %s`) can show the same blank text; they are listed as a follow-up and only the retry loop is changed here.
8. **Failure memo and shared in-flight build.** Module-level state guarded by a `threading.Lock`: `{sensor, failed_at (monotonic)}`. A build that ends without a usable profile (fewer than the floor of days fetched, whether because chunks failed, the deadline passed or the loop aborted early) sets it; a partial window that meets the floor is a usable result, so it clears the memo like a full one (its cost per call is bounded by the 60 s deadline, and HA is mostly responding). A history request that fails permanently (for example HTTP 401) also leaves a chunk unfetched, since `get_power_history_batch` returns None for every failure; it is attempted once and counts toward the floor like any failed chunk. At the start of a call, if the memo matches the configured sensor and `now - failed_at < cooldown`, the call skips fetching and runs the fallback chain (last good, then synthetic/demo), setting the same truthful status. Success clears it; a changed sensor ignores it. Cooldown is 300 s: transient stalls seen in prod were short and isolated (one-off failures spread over hours on 2026-11-05 to 11-07), the profile changes slowly, a planner run needs only a baseline, and 5 minutes bounds an outage to one 60 s deadline per window (about 20 percent worst-case duty) while letting the next planner cycle after recovery fetch live. Concurrent calls in the same event loop await one shared `asyncio.Task` kept in a per-loop dict (same keying idea as `get_ha_http_client`), removed in `finally`, so the two planner calls and an API call arriving together do one build. A task or future cannot be awaited across loops, so calls on different loops are not coalesced; the cooldown still bounds them. Only transient failures set the memo; empty history and implausible data do not (they are not outages and keep their messages). The debug route passes an explicit `force_refresh=True` to bypass the cooldown (it exists to test fetching); ordinary routes do not.
   - Alternative: cache successful profiles for a few minutes as well. Rejected: not needed for outages and would hide fresh data; planner cadence already limits calls.
   - Alternative: a full circuit breaker with half-open probes. Rejected: a fixed cooldown gives the same bound with far less state.
   - Alternative: coalesce through a process-wide lock instead of per-loop tasks. Rejected: a lock held across a 60 s await would block unrelated loops.

## Risks / Trade-offs

- [A stored profile can be up to 7 days old and not match a sudden change in household load] -> Age shown in the status; Aurora load forecasts remain the primary source and this profile is the baseline/fallback; the age limit bounds the error.
- [A cooldown can serve a fallback for up to 5 minutes after HA has recovered] -> Fallback is the stored profile with its age, which is the same quality the user would have had during the outage; the cooldown expires on its own and an explicit refresh bypasses it.
- [Calls on different event loops are not coalesced] -> The cooldown bounds their cost; the planner calls run on one loop.
- [Retries add up to ~25 s per failing chunk before giving up] -> Bounded by the deadline; the planner already waits for this call today (7 x 12 s worst case).
- [Partial window skews the profile] -> Argued above; floor of four days; status tells the user.
- [Clearing `demo` on a successful live build changes when the banner disappears] -> Intended; test that ML-owned reasons are untouched.
- [Persisted file corrupt or from an older schema] -> Validated on read; ignored with a log line, never fatal.

## Migration Plan

No schema or config change. On first deploy there is no stored profile, so the first transient failure before the first successful build still falls back as today. Rollback is a revert; the stored file is ignored by older code. Pure code and data; no production action in this change.

## Open Questions

- Attempt timeout (20 s read) and deadline (60 s) are reasoned from the ~3.2 s normal request, not from a measured stall duration. They can be tuned after looking at HA response times around the 2026-11-05 stalls; no spec text depends on the exact numbers.

## Addendum: follow-ups (2026-11-08)

- Executor logging: the remaining `%s`-of-exception sites that could print an empty message now use `describe_exception`: the executor write, mode lookup and notification paths, plus other HA/network handlers in `executor/` and `backend/` (logging only, no behaviour change).
- Timezone: the load profile slot mapping read a hard-coded `Europe/Stockholm`. It now uses the configured `timezone` through `_configured_timezone` (default `Europe/Stockholm`, unknown names fall back to the default with a warning). The `Europe/Stockholm` default in the `parse_ha_datetime_state` caller keeps its except-branch fallback, now via the same default constant.
