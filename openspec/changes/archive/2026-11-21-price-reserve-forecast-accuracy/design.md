## Context

`planner/strategy/price_reserve.py` sizes a reserve while `min(P_h, own_day_cheapest_cost) - known_cheapest_cost > threshold` (threshold from `RISK_RESERVE_THRESHOLD_SEK`, risk 3 = 0.10 SEK/kWh), all-or-nothing, no hysteresis. `planner/pipeline.py::build_price_reserve_inputs` feeds it the latest-issue `spot_p50` for the 24 h after the published-price horizon, converted by `spot_to_import_price`. A synthetic check shows moving the unseen-day cheapest price from 3.40 to 3.50 against a known 3.36 swings the reserve from 0 to 8.42 kWh, so any forecast error larger than the threshold flips the decision.

`/api/price-forecast/accuracy` (`backend/api/routers/price_forecast.py`, `_fetch_accuracy_rows` + endpoint) already computes D+1 MAE and bias over 7 days, but only the UI uses it.

Verified against HEAD (see tasks 1.x for re-checks during implementation):
- `export_price_sek_kwh` IS raw spot in SEK/kWh: `calculate_import_export_prices` (`backend/core/prices.py:~490`) sets `export_price = spot_price_mwh / 1000`, and the recorder/backfill store that value (`backend/recorder.py:~536, 613, 724`). It is comparable to `spot_p50`. No endpoint fix needed.
- `price_forecasts` keeps only the latest issue per `(slot_start, days_ahead)` (pruning in `ml/price_forecast.py:~350`), so the accuracy join compares the latest D+1 issue to actuals.
- Residual caveats, not blocking: `get_nordpool_data` can contain `price_source == "forecast"` slots and the recorder backfill does not filter them (only future slots, so past observations are real); the join is a string equality on `slot_start` and the 7-day filter compares ISO strings with `datetime('now')` (UTC). Both are existing endpoint behaviour, preserved for `days_ahead = 1` so output stays identical.
- Existing `price-forecast-accuracy-kpi` spec says insufficient data returns `sample_days: 0`, code returns the actual count (0 or 1). Code behaviour is kept; spec is not touched here.

## Goals / Non-Goals

**Goals:** make the reserve robust to a biased or noisy D+1 forecast using the system's own measured accuracy; keep one source of truth for accuracy; be explainable; degrade to today's behaviour.

**Non-Goals:** hysteresis (needs persisted state across planner runs; follow-up change), new config keys, per-user constants, changing sizing maths, EV deferral changes.

## Decisions

0. **Why the original unseen-only correction is wrong (code trace).** `price_horizon_end = df.index[-1]` (`planner/pipeline.py:~1798`) and the known window is `df[df.index >= now_slot]` (`build_price_reserve_inputs`, `~1161`). Before `TOMORROW_PUBLISH_HOUR` (13, `backend/core/prices.py:27`) `get_nordpool_data` appends the D+1 forecast fallback slots tagged `price_source == "forecast"` (`backend/core/prices.py:~345-375`, source `get_d1_price_forecast_fallback`, `ml/price_forecast.py:~495`, which since commit 58945962 reads tomorrow's local date across all `days_ahead` values and keeps the latest issue per slot; each record gets `forecast_days_ahead` from its source row). The known window then contains forecast slots and the unseen window is D+2. The reported flapping (03:18-06:20) is in this period. Correcting only the unseen side would compare corrected forecasts to biased forecasts. Both sides must be on the same corrected basis. Real slots stay untouched.
1. **Shared module `ml/price_accuracy.py`** (next to the other price-forecast code; the router already imports `ml.price_forecast`). Contents: `fetch_accuracy_rows(db_path, days_ahead=1)` (the current SQL with `days_ahead` bound as a parameter; `1` reproduces today's query exactly), `compute_forecast_accuracy(rows) -> ForecastAccuracy` (frozen dataclass: `mae`, `bias`, `debiased_mae`, `sample_days`, `status` = `ok` | `insufficient_data`), and `load_forecast_accuracy(db_path, days_ahead=1)`. The endpoint maps the `days_ahead=1` result to its existing JSON (4-decimal rounding, same `insufficient_data` payload). The planner calls the same function for each horizon it needs. Alternative of the planner calling the HTTP endpoint was rejected.
2. **Per-slot horizon, not a flat D+1 number.** `days_ahead` is relative to the issue date, and the unseen window is mostly D+2 (day after tomorrow, `days_ahead = 2` from today's issue, 3 from yesterday's issue when the run is before today's 06:00 forecast). D+2 error is larger than D+1 error, so applying D+1 accuracy would understate noise exactly where the correction matters. Checked: `generate_price_forecasts` writes `days_ahead` 1-7 on every run (`range(1, 8)` daily at 06:00, `range(2, 8)` post-publication, `backend/services/scheduler_service.py:~478, 578`), and pruning keeps the latest issue per `(slot_start, days_ahead)` (`ml/price_forecast.py:~350`), so `days_ahead = 2` (and 3...) rows with actuals exist for the same 7-day window and the same join works with a different bound parameter. It is therefore cheap and chosen over documenting D+1 as a lower bound (one extra bound parameter, no schema change, strictly more correct).
   - Each unseen slot's horizon is the `days_ahead` of the forecast row selected as latest issue. `planner/strategy/ev_deferral.py` gains `fetch_forecast_spot_with_horizon_sync` returning `(spot, days_ahead)` per slot; both it and `fetch_forecast_spot_sync` use one private latest-issue reader (`_fetch_latest_issue_sync`), and the original keeps its signature, result and SQL (it does not read `days_ahead`, so databases or fixtures without that column still work).
   - Known-window forecast-fallback slots use the horizon carried on their price record as `forecast_days_ahead` (see Dependency). Between 00:00 and the 06:00 daily issue they come from yesterday's issue (horizon 2) and afterwards from today's (horizon 1). The key is carried by `_process_nordpool_data` (`backend/core/prices.py:~551`) only on `price_source == "forecast"` slots, so published slots never have it; if it is absent on a forecast slot (older data path) the horizon is 1.
   - Fallback chain per horizon: that horizon's accuracy if `status == ok`, else D+1 accuracy if ok (a documented lower bound), else no correction for those slots.
3. **De-bias both sides, same basis.**
   - Unseen window: `spot - bias_h` before `spot_to_import_price`.
   - Known-window forecast slots: the df holds import prices, not spot. Import price is linear in spot with slope `1 + VAT` (`calculate_import_export_prices`), so the corrected import price is `import - bias_h * k` (`h` = the slot's `forecast_days_ahead`, default 1) with `k = spot_to_import_price(s + 1) - spot_to_import_price(s)` taken from the existing converter (time-of-use fees cancel). This avoids needing raw spot in the planner df.
   - Real (`nordpool`) known slots are never adjusted. Negative prices are not clamped.
   - Only `PriceReserveInputs.known_slots` is corrected. The planner df, the solver adapter and the schedule keep the uncorrected prices, so Kepler is unchanged and no scope is added.
4. **Carrying `price_source`.** Traced: `get_nordpool_data` output keeps `price_source` per slot (`_process_nordpool_data`, `backend/core/prices.py:~540-553`) and `input_data["price_data"]` holds it (`backend/core/forecasts.py:~850-871`), but `build_price_dataframe` (`planner/inputs/data_prep.py:~45-90`) drops it, so the planner df has no source column. Rather than widening the df (which feeds Kepler and many other consumers), the pipeline builds `forecast_slot_starts: Mapping[datetime, int]` (slot_start to `days_ahead`) from `input_data["price_data"]` entries with `price_source == "forecast"`, using the entry's `forecast_days_ahead` (1 when absent or invalid; `forecast_slot_horizons` in `planner/pipeline.py`), and passes it to `build_price_reserve_inputs` as a new optional argument (default empty = nothing corrected on the known side).
5. **Noise gate.** `typical_error_h = debiased_mae_h` (mean of `|e - bias_h|`; not plain MAE so a constant offset is not punished after it was removed; not RMSE/percentiles to stay consistent with the displayed MAE and robust to spikes). The gate uses the maximum of `typical_error_h` over the horizons actually used by forecast-sourced slots in either window (the gain compares two sides whose errors are not known to be independent or correlated, so the larger one is the conservative, assumption-free choice). Scaled to import domain with the same `k` as above. `effective_threshold = max(risk_threshold, typical_error_import)`. Risk appetite 5 (threshold 0) is still gated: user choice sets a floor, measured noise can raise it. Efficiency division and cheapest-hours averaging are not applied (slot-level MAE is a conservative proxy).
6. **Data flow.** `build_price_reserve_inputs` loads accuracy for the needed horizons in one `asyncio.to_thread` call, corrects `unseen_prices` and the forecast-sourced `known_slots`, and stores on `PriceReserveInputs`: `forecast_error_sek_kwh` (import domain), `forecast_bias_sek_kwh` (bias of the horizon covering most unseen slots, spot domain, for display), `accuracy_by_horizon` (`{days_ahead: {bias, debiased_mae, sample_days, used_fallback}}` for the debug dict) and `accuracy_fallback` (True when no slot was corrected). All defaults reproduce current behaviour. `evaluate_price_reserve` computes the effective threshold and passes it as `threshold_sek_kwh` (`size_price_reserve` signature unchanged). `PriceReserveResult` gains the same fields with defaults.
7. **Fallback.** For any horizon: fewer than 2 sample days, no rows, or any exception (warning log) means that slot group is not corrected. If nothing could be corrected, bias and error are 0, `accuracy_fallback = True`, effective threshold = risk threshold: identical numbers to today. An accuracy failure never sets `error="forecast_read_error"` (that would deactivate the reserve); only the forecast read does.
8. **Explainability.** New debug keys always present: `price_reserve_effective_threshold_sek`, `price_reserve_forecast_bias_sek_kwh`, `price_reserve_forecast_error_sek_kwh`, `price_reserve_accuracy_fallback`, `price_reserve_forecast_accuracy` (per-horizon map) and `price_reserve_corrected_known_slots` (count of forecast-sourced known slots corrected). `price_reserve_threshold_sek` keeps the base risk threshold. Strategy event details carry the same keys; the active message mentions the correction when applied. Frontend `api.ts` types are additive and optional.

## Dependency

`forecast-slot-benchmark-and-dead-config-fixes` is implemented, archived and committed (58945962, `openspec/changes/archive/2026-11-21-forecast-slot-benchmark-and-dead-config-fixes/`). It makes `get_d1_price_forecast_fallback` choose tomorrow's slots by date from the latest issue regardless of `days_ahead`, sets an int `forecast_days_ahead` on each fallback record, and `get_nordpool_data` carries it (with `price_source: "forecast"`) into `input_data["price_data"]` only for forecast-sourced slots. This change reads `forecast_days_ahead` to pick each known-window forecast slot's horizon. If the key is absent (older data path) the horizon is treated as 1. Horizons by time of day:
- 00:00 to the 06:00 issue (pre-issue): known forecast slots horizon 2 (yesterday's issue), unseen window horizon 3.
- After the 06:00 issue, before publication: known forecast slots horizon 1, unseen horizon 2.
- After publication: no forecast-sourced known slots, unseen horizon 2.
Per-slot fallback chain everywhere: own horizon, then D+1, then no correction. The gate uses the largest de-biased MAE of the horizons in use.

## Risks / Trade-offs

- Noisy forecasts now suppress the reserve more often: intended (it was acting on noise), but users with a genuinely volatile market lose some pre-charging. The reserve reappears when real gaps exceed typical error.
- Known and unseen sides can sit on different horizons (for example 2 and 3); a missing horizon falls back to the D+1 bias, the best available and strictly better than none.
- 7-day window lags regime changes; de-biasing can mis-correct for a few days. Accepted, same window the KPI shows.
- Without hysteresis, flapping can still occur near the effective threshold; the gate only makes it rarer. Tracked as follow-up.
- Slot-level MAE vs cheapest-hours average is a deliberate conservative simplification.
