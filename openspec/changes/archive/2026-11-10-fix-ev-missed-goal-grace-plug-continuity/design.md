## Context

`resolve_ev_effective_deadline` (planner/pipeline.py ~224-270) grants grace when `ha_state["plugged_in"]` and SoC < target, with no knowledge of *when* the plug session began. Plug state lives in module-level in-memory dicts in `backend/core/ev_plug.py` (`_last_known_plugged`), fed by `ev_live_state.py`, `ha_client.py` and the WebSocket handler. `compute_ev_goal_diagnostics` receives `now_dt`, which is the 15-min-floored slot time (~1442), while the real time is `real_now` (~1435-1441, used at ~1696-1700 for remaining slot-0 hours).

## Goals / Non-Goals

**Goals:** grace only for true continuity (with a SoC-based check when history is lost); grace never costlier than the next goal; correct partial-slot diagnostics; universal logic (no per-user values).
**Non-Goals:** EV planning on forecast D+1 prices (separate change).

## Decisions

**D1 Plug-session start with unplug debounce, persisted in the existing EV state file (no DB schema change).** `ev_plug.py` tracks `_plug_session_start` and `_first_unplugged_at` per charger inside `remember_plug_state`. A plugged reading after a known not-plugged reading starts a session at `now`. The first not-plugged reading of a session records `first_unplugged_at`; the session only ends once not-plugged has persisted `>= EV_UNPLUG_DEBOUNCE_MINUTES` (named constant, 10). A plugged reading inside that window clears `first_unplugged_at` and keeps the original start (flicker); a plugged reading after the window is a replug and starts a new session. Unreachable readings never reach this code, so they touch neither value. The logic is vocabulary-independent (it consumes the already-interpreted boolean). `plug_session_start(charger_id)` is exposed and added to `ha_state`. The grace continuity check (`session_start <= missed`) therefore treats a flicker across the deadline as continuous, including while still inside the window (the start is retained until the debounce expires; actual charging still needs a plugged reading).

**D1b Persistence across restarts.** The session is stored per charger in the existing locked, atomic state store (`backend/core/ev_state.py`, `data/ev_multi_day_state.json`) via `update_ev_state`, under the charger entry key `plug_session` = `{"start": iso, "first_unplugged_at": iso | null}` (same pattern as `manual_charge`: shares the entry, is not a goal; the planner's entry rewrite and the goal-clear path preserve it, and the charger API view excludes it from the goal fields). It is written only when `(start, first_unplugged_at)` changes (transitions), never on repeated same-state readings; write failures are logged and swallowed. On the first valid reading per process the saved session is read once: it is restored only if the charger reads plugged and the saved `first_unplugged_at` is absent or younger than the debounce; an unplugged first reading only continues a debounce that was already running. Otherwise the history is unknown (`None`) and the saved record is removed, which falls through to D2b (SoC-drop check). Missing, corrupt or old-format files read as unknown history. Writes use the file lock (multi-process safe) and happen only on transitions from the existing synchronous call sites, so the event loop is not hit per reading. Trade-off: a car that left and returned while Darkstar was down (saved `first_unplugged_at` absent) looks continuous; D2b's SoC check (applied for restored sessions too) covers the driven case.

**D2 Continuity rule.** (session-start semantics per D1/D1b) Grace requires: grace_h > 0; plugged (or unreachable with last known plugged); SoC present and not `stale`; SoC below `target - tolerance` (D5); and continuity: `session_start` is not after `missed` (known `<= missed` or `None`) and D2b does not show a drop. Existing `last_updated`, expiry and next-deadline-cap rules unchanged. A replug after the deadline (session_start > missed) returns no grace, which also covers the SoC-drop case since the replug creates a new session.

**D2b SoC-drop check.** Whenever grace would otherwise be granted (known `session_start <= missed`, or unknown), compare current SoC with the SoC at/just before the missed deadline (`soc_at_missed_deadline`). If `soc_at_deadline - current_soc > EV_SOC_DROP_NOISE_PERCENT` (named constant, 1.0 point, absorbs sensor jitter) the car was driven: no grace. Otherwise (equal, rose, within noise) grace continues. If no deadline SoC is available: legacy behaviour (grace allowed). Source, verified in code: (a) HA history of the charger's `soc_sensor` through the existing history client (`backend/core/ha_client.py` `get_power_history_batch`, one request; take the last state at or before `missed`, fall back to none if HA returns nothing or only non-numeric states). Not usable: the persisted goal store `current_soc_percent` (overwritten every planner run, no timestamp, so it is not the value at the deadline) and `slot_observations` / `planner_learning.db` (records battery SoC only, no EV SoC column). The async read happens in the layer that builds `ha_state` and only when plugged, `session_start` is not after the missed deadline, SoC below target-tolerance and a missed deadline inside the grace window exists, so the common path makes no HA call; the result is passed as `ha_state["soc_at_missed_deadline"]` and `resolve_ev_effective_deadline` stays pure. Implementers must verify the history helper's signature/parsing (it is power-oriented) and generalise if needed.

**D3 Cost-aware grace via price-derived soft penalty.** Each charger input carries `shortfall_penalty_sek_per_kwh`; regular goals keep `EV_SHORTFALL_PENALTY_DEFAULT` (50). For a grace charger the adapter computes, from the slots' import prices between now and the next regular deadline (`next_deadline`, capped at the horizon end; carried in plan state):
`penalty = max(min_price, 0) + max(EV_GRACE_SPREAD_FRACTION x (max_price - min_price), EV_GRACE_MIN_MARGIN_SEK)`
with `EV_GRACE_SPREAD_FRACTION = 0.25` and `EV_GRACE_MIN_MARGIN_SEK = 0.05`.
Rationale: the solver buys a slot at price p only while p < penalty, and unmet grace energy is picked up by the rolled goal at roughly the cheapest price before the next deadline. Anchoring on that cheapest price plus a fraction of the spread means grace buys only slots near the cheapest available price, independent of market level (cheap day, expensive day, different currencies), and a price spike is never bought into. It is single-pass and deterministic, unlike a two-pass solve capped by the next-deadline plan price. Edge cases: flat prices (spread ~0) give min_price + margin, so grace still charges at the flat price (no cheaper alternative exists); negative minimum prices are floored at 0 so the penalty stays positive and grace is not silently disabled; unknown/empty prices use `EV_GRACE_PENALTY_FALLBACK_SEK` (2.0 SEK/kWh, a last-resort constant used only when no price exists to derive from; the target stays soft and nothing raises). Shortfall of a grace target is reported as grace shortfall, not a missed real goal. Replay the Torleif scenario at Kepler level (5.8 now vs 2.4 overnight: penalty ~3.2, no grace charging) even though D2 already drops grace there.

**D5 Missed-goal tolerance.** New per-charger `ev_chargers[].missed_goal_tolerance_percent` (percentage points), planner constant default `MISSED_GOAL_TOLERANCE_PERCENT_DEFAULT = 5.0`, `0` disables the tolerance, negative/invalid values fall back to the default (negative is clamped to 0). In `resolve_ev_effective_deadline` the check `soc >= target` becomes `soc >= target - tolerance`. It applies only to the catch-up grace: normal goal planning (`_calculate_required_kwh`, shortfall, deadlines) is unchanged and still targets the full target SoC. Config: default added to `config.default.yaml` next to `missed_goal_grace_hours`; no migration needed (grace hours has none either; an absent key resolves to the code default, covered by a test); UI field added next to Missed Goal Grace in `EntityArrayEditor.tsx` (type, new-charger defaults, NumberInput, step 1, min 0, max 20). `frontend/src/config-help.json` and `settings/types.ts` carry no per-field entries for grace hours (only the generic `ev_chargers` help), so they are not touched; the executor does not read it (`executor/config.py` unchanged).

**D4 Diagnostics use real now.** Pass `real_now` into `compute_ev_goal_diagnostics`; eligibility uses `s.end_time > real_now` with slot 0 capacity = `first_slot_remaining_h`. If sum over eligible slots of remaining hours x max kW (charger_power_limits max) < required (after losses) the reason is `deadline_too_close`. `_warn_on_zero_scheduled_active_goals` scales min_chunk by slot-0 remaining time when slot 0 is the only candidate.

## Risks / Trade-offs

- Restart mid-session restores the saved start (D1b); with nothing restorable the SoC-drop check applies (D2b), and if HA history is unavailable, legacy behaviour (accepted). A car driven and recharged back to within noise of the deadline SoC is indistinguishable (accepted, rare).
- Missed WebSocket events could mis-set transitions; REST reads call the same `remember_plug_state`, so it self-corrects on next valid reading, but a very short unplug/replug between polls is invisible.
- Spread fraction 0.25 and margin 0.05 are judgements validated by tests across price regimes, not per-user values. The 2.0 fallback applies only when prices are unknown.
- Tolerance 5 points means up to 5 points below target are left for the next regular goal; users wanting strict recovery set 0.
